# Design Doc (spec 型) template

`/sdd-design` の既定 template。実装から逆算し、受け入れ条件 (ID を振らない表) を軸に本文を組む。12 節のフル版は `design-doc-template.md`、書き方の規範は `../guidelines/writing/design-doc-protocol.md` が canonical。

## 節構成 (この順で書く)

team の DD 14 本 (2026-09-05 時点) と突き合わせて決めた形。書くことが無い節は作らない (「該当なし」の節を残さない)。

```markdown
# Design Doc: [機能名 (merge 後に user か運用者ができること)]

- Status: draft
- Created: YYYY-MM-DD
- Issue / PRD: #XXXX / [PRD path]

> **正本の注記** (後から修正するときはここに日付付きで書き、本文は書き換えない)
>
> なし

## 1. 何を実現するか

## 4. Implementation Surface (何をどのくらい作るか。PR 分割できる粒度のシステム変更面)
冒頭に合計を 1 行書く (例: API 変更 5 本 (Read 3 / Write 2)、Read の能力 1、DB 新規 table 2 / 列追加 1、画面 4)。`Read n / Write n` は Backend API 表の種別列の内訳を指し、能力の表の行数は「Read の能力 n」のように別の語で書いて API の内訳より後ろに並べる (`dd-gate.sh` は最初に現れた `Read n` を採用する)。下の見出し名と 1 列目の header は言い換えずにそのまま使う (`dd-gate.sh` がこの文字列で表を特定する)。Frontend 表の行は変更がある画面だけにし、画面の変更が無いときは表を作らず合計 1 行に「画面 0」と書く (Data Schema の「DB 変更なし」と違い、「変更なし」の行を追加すると合計と行数が食い違う)。行の名前は endpoint (`GET /v2/...`) と画面名の具体名で書く (team の既存 DD は目次だけで作る量が数えられる)。endpoint は route 定義で実在と形 (1 件取得 / 一覧) を確かめ、無ければ「新規」と書く。method 名・SQL・file 名は書かない。field の詳細は Appendix B へ
### Backend API
| endpoint | 種別 (Read / Write) | 変更 (新規 / 既存拡張) | 主な責務 |
### Required Read Capabilities
| Read | 新規 / 既存 | 用途 |
### Required Write Capabilities
| Write | 新規 / 既存 | 条件・結果 |
### Frontend
| 画面 | 種別 (新規 / 更新) | FE 側の logic (表示するだけ / 状態や制御がある) |
### Data Schema (table 設計。無ければ「DB 変更なし」1 行)
新規 table と既存 table の列追加を table ごとに書く。「別 table にするか列を追加するか」「一意制約の範囲」は完成形を変える決定なので DD で固める。DDL 全文と SQL、migration 手順は書かない (`design-doc-protocol.md` の 5 列表に合わせる)
| table | 変更 (新規 / 列追加) | 用途 |
変更後の関係を ER 図 (mermaid `erDiagram`) で 1 つ描く。新規 table と列追加する既存 table、それらが参照する既存 table だけを載せ、新規は entity 名の後に「新規」と書く。線は FK と多重度 (1 対 0..1 / 1 対 0..N) を表し、列は主キーと FK 列だけ書く (5 列表と二重にしない)。`<details>` に入れず本文に置く (判断に必要な図。user 要望 2026-09-06)
#### [table 名] (新規 / 列追加)
| カラム名 | 型 | NULL | デフォルト | 説明 |
- 先例: [同じ役割の列 / 制約の repo 内の件数と採用 (例: 無効化 disabled_at 3 件 / flag 0 件 → disabled_at を採用。外れるなら理由)]
- index / 制約: [UNIQUE の範囲、FK、index の列を bullet で。同じ親の中で重複を許さない列の組 (表示名 / 表示順 / 識別子) を必ず書き、許すならその理由を書く]
- 不変条件の担い手 (既存の制約 UNIQUE / FK / NOT NULL / CHECK / 排他制御を削除または緩めるときだけ): [何を守るか / 今どの仕組みが守るか / 削除する制約が防いでいた場面 / 削除した後の担い手 の 4 列表 (`design-doc-protocol.md` 「図表の型」)。「削除した後の担い手」が別 PR になるなら、その間の保険 (読み取り側の吸収 等) を Release の節に書く]

## 5. 受け入れ条件
[PRD があるとき] PRD 「受け入れ条件」 は全て満たす、と 1 行で引き受け、PRD の条件には 新たに ID を割り振らない (PRD の番号 U-n / A-n 等で参照する)。ここに書くのは PRD に無い条件だけで、2 群に分ける。表の先頭に `No` 列 (1, 2, 3 の通し番号) を置いてよいが (列名を `#` にしない。番号が issue への参照と紛らわしくなる)、読みやすさのためだけで、本文の見出し / 決定事項 / 後段の command からは番号でなく条件の文で指す (team の DD に ID の慣習が無い。user 決定 2026-09-05)
### 5.1 PRD に書き戻す要件: user か運営から見える振る舞いを決めたもの (PRD の要件の変更、UX の決め、古い client の扱い、表示の欠けの補完)。「PRD A-n を変更 / PRD U-n に追加」と書き、PRD author の確認を経て PRD の更新 PR で反映する。反映後は PRD の番号で参照してここから消す
### 5.2 DD が持つ境界: データの整合や API の設計から出る不変条件 (既定値、UNIQUE 制約の帰結、再送の冪等性、記録が無いときの整合表示)。PRD author の判断を要しない。次の 3 つは毎回問い、条件になるものだけ表へ追加する (該当しなければ書かない) (2026-09-06 に抜けて、実装の後半で PR 3 本になった): (a) 既に参照されている master 行の変更 (無効化 / 名前変更 / 削除 / 並べ替え) を許すか、許すなら参照側の表示はどう変わるか (b) 同じ内容の再送は書き込まずに成功にするか (c) 切替 (要否 / 有効無効) の逆方向を許すか、許さないなら理由
[PRD が無いとき] | No | 由来 (R-n) | 条件 | の表。条件は [誰が] [何をすると]、[何が] [どうなる]
  - 境界: [0 件 / 上限 / 同時実行 / 再送 / 参照済み行の変更 / 切替の逆方向 のときの結果]
  - 失敗時: [何が起きて user に何が見えるか]

## 6. 振る舞い (順序か分岐がある場面だけ。受け入れ条件の表を読めば分かる場面は節を作らない)
[書くのは、条件の表 1 行では追えない場面に限る: 複数の条件が 1 つの操作の中で順に適用される、経路が 2 つ以上ある (決済失敗と期限切れの戻し処理が別の入口)、同時実行、状態遷移。判定は「図か番号付き手順として書けるか」で、書けない節は条件表の行で足りるので作らない。**この条件に当たる場面では図か番号付き手順を置く (文章だけで説明しない)**。分岐のある受け入れ条件が 2 行以上あるのに節へ図も番号付き手順も無いと、`dd-gate.sh` の `behavior-diagram` が WARN にする。「運営が登録する」「ユーザーが選ぶ」のような正常系の言い直しは書かない (2026-09-06 に 7 節中 4 節が条件表と決定の言い直しだった)]
```

## 外見

- 行数目安 (`design-doc-protocol.md` 「テンプレ選択」 の 300 行) は本文 (Section 1 〜 Section 12) に当て、用語表 / Implementation Surface の表 / Appendix / `<details>` の図は別枠で数える

- 冒頭は「項目 / 値」の 2 列表 (Status / Created / Last Updated / Related Issue / Related PRD を link で)。その下に正本の注記の blockquote
- 用語は分類ごと (エンティティ / 識別子 / 状態 / 操作・画面) の「用語 / 説明」表にし、本文で使う語を PRD と重複してもすべて記載する。説明は日本語だけで書き、DB 列名や field 名は添えない (列名は Data Schema の 5 列表に置き、用語表には書かない)
- 節名は team の DD に合わせて英語にする (Overview / Glossary / Current State / Implementation Surface / Acceptance Criteria / Proposed Design › Data Flow / Design Decisions / Non-Goals / Deployment and Release Plan / Open Questions / Appendix。Design Judgement は置かず、Review Points は任意)。小節は日本語でよい
- 段落を作らない。節の本文は入れ子の箇条書きで、「前提 → 結果 → 拒否」のような構造を上位と下位の階層で表す。ただし 1 行は日本語の文として読める形にし、記号 (`+` `/` `→`) で語をつないだ句や体言止めの羅列にしない。表の cell も同じで、短い文にする。「現状との差」のような各節の定型行は Current State に集約して繰り返さない (user 指摘 2026-09-05: 書きすぎに見える。抽象表現でよいが説明は日本語の文で)
- 主語と対象を省かない。「要否を変える」でなく「運営が景品のサイズ要否を変える」のように、誰が (ユーザー / 運営 / サーバ / 画面)、何の (景品 / サイズ行 / 注文)、何を、まで書く。抽象的な言い回しでよいが、行為者と対象は具体にする (user 指摘 2026-09-05)
- 動作の主体をそろえる。サーバや運営が行う動作を、対象物 (サイズ行 / 案内文 / 再依頼) を主語にして書かない (「サイズ行は変更を拒否する」でなく「サイズ行については変更を受け付けない」)。主語を省くなら文書全体をサーバ主語で統一する
- chat の癖語を文書の語に置き換える: 引く → 参照する、決め → 決定 / 動作、扱い → 動作、足す → 追加する、出す → 表示する / 返す、`取り直す` → 再取得する。条件と結果で同じ語を使わない (「確定した時点で…確定せずに」のような衝突)。(user 指摘 2026-09-05: 主語のねじれと内輪の言い回しで不自然になった)
- 最上位の節の間に `---` を置く。節をまたぐ参照は `[節名](#anchor)` の link にする
- 受け入れ条件 / 決定事項 / CUD / 未確定は表で書く。**有効** / **無効** のような状態語と「案 A (採用)」は太字にする
- 大きい図 (ER / sequence) と Appendix は `<details><summary>展開して読む (対象)</summary>` に入れる。本文で判断に必要な図 (state / flowchart) は入れない
- 設計判断が 4 つ以下なら Section 7 の表、5 つ以上なら「決定 n」小見出しで本文に記載する。Appendix に比較表を分けない (本文と Appendix で決定が二重になる)
- 表は prettier (`npx prettier --parser markdown`) で列幅を合わせてから出す

## 図の使い方

- 図を置くのは順序か分岐がある箇所だけ: 同時実行 (sequence)、状態遷移 (state)、リリース手順 (flowchart)、schema の関係 (ER。現状は Section 3.2、変更後は Data Schema)。CUD の条件や決定事項は表のまま
- **該当する箇所では図を置くのが既定で、文章だけの説明に替えない**。図の代わりに番号付き手順を記載してもよい。情報の構造で表現を決める (単純なもの = 表、順序だけ = 番号付き手順、分岐と再結合 = 図)。逆に、該当しない箇所へ図を増やさない (図の作成自体が仕事になる)
- 正常系だけの sequence 図は本文の bullet と同じ情報なので置かない。競合や失敗の分岐がある場面に限る
- mermaid の label に `<br/>` を使わない (描画されない viewer がある)。flowchart の node は 10 文字前後に収め、説明は図の下の 1 段落に記載する。state 図は `state "表示名" as id` と遷移だけで表現し、複合 state の中に説明を記載しない (2026-09-05 実測)
- 本番の数値 (分布 / 比率) が取れたら Section 3.1 に表かグラフで置き、決定の根拠にする

## 各節の書き方

| 節 | 書く | 書かない |
|---|---|---|
| 1. 何を実現するか | user の言葉。今との差 | 実装の構造、技術選定 |
| 5. 受け入れ条件 | 真偽が判定できる文。境界と失敗時を下位 bullet に | 「適切に」「必要に応じて」、実装手順 |
| 6. 振る舞い | 前提 → 結果。現状は実物で確認した挙動 | 識別子 (Appendix へ)、層の話 |
| 7. 決定事項 | 実装者が code を読んでも決められない点 | 関数名 / 層の分け方 / 読み込み済みの再利用 |
| 9. 設計判断 | 仕様の選択肢としての比較 | 「再実行 vs 再利用」のような実装の書き方の比較 |

## 節を削る判定

- 選択肢が無かった機能では 9 を削る。data も画面も増えない変更では 4 の該当行だけ維持する
- どの受け入れ条件にも対応しない節や表は削る。逆に、どの節にも説明が無い受け入れ条件は 6 に見出しを追加する。対応は書き手が確かめる作業で、本文に番号を記載して示さない
- Appendix の図は、5 と 6 を読んで順序が追えないときだけ追加する (図が無いと読めない doc は本文が不足している)

## /sdd-plan との接続

- `/sdd-plan` は 5 の受け入れ条件を条件の文 (先頭 20 字程度) で引用して Phase へ割り当て、各 Phase の完了条件にどの test で確かめるかを記載する
- Phase の合計が受け入れ条件の総数を過不足なく覆うことを `/sdd-plan` Step 4 で確かめる。覆えないときは Design Doc 側の 5 が不足しているので、`/sdd-design --update <path>` で条件を追加してから戻る
