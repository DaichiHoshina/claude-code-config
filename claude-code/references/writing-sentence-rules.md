# 文単位の品質規約 (詳細)

`guidelines/writing/PRINCIPLES.md` の `## 文単位の品質規約` の詳細層。段落 / 媒体構造は PRINCIPLES.md 本体が扱い、この file は文脈を読んで判断する観点を扱う。textlint preset (ja-technical-writing / JTF-style) の知見は診断候補であり、数値を合否や書き直し条件にしない。深い書き直し / `/jp-fix` 実行時に参照する。

## 文を分ける基準

技術文書、web、短文のいずれも字数上限は設けない。条件・因果・主語と述語の対応を一度で追えない場合だけ、意味の切れ目で分ける。同じ論点を説明する文は、つながりが明確なら同じ段落に維持する。

## 読点は個数で判定しない

読点 (`、`) は係り先を明確にするために使う。個数だけで文を分けず、読点が多い文は語順や節の関係を実際に読んで確認する。

## 読点は係り受けの境界に打つ

読点を打つ位置は係り受けで決める。息継ぎや見た目のリズム目的では打たず、係り先を固定する記号として使う。

1. 長い修飾語が並び、境界を誤読する場合に打つ
2. 語順の原則 (長い修飾語が先) を崩して短い語を前に出したとき、その直後に打つ

- NG: `渡辺刑事は血まみれになって逃げた賊を捕まえた。` (血まみれなのが刑事か賊か 2 通りに読める)
- OK: `渡辺刑事は、血まみれになって逃げた賊を捕まえた。`

出典: 本多勝一『日本語の作文技術』読点の 2 原則。

## 修飾語の語順 4 原則

係り先の誤読は読点でなく語順で防ぐことを優先する。

1. **長い修飾語を先に**、短い修飾語を被修飾語の直前に置く
2. **述語を含む節を先に**、述語を含まない句を後に置く
   - NG: `厚手の白い横線の引かれた紙` (「白い横線」と誤読する)
   - OK: `横線の引かれた厚手の白い紙`
3. **大状況 (時期・環境) から小状況 (個別対象) へ**の順に置く
   - NG: `決済 API で今朝の deploy 後に error が増えた`
   - OK: `今朝の deploy 後に決済 API で error が増えた`
4. **前置修飾節を入れ子にしない** (逆茂木型の禁止)。長い修飾節が 2 つ以上必要なら文を分割する
   - NG: `昨夜 deploy した際に発生した、retry 処理が二重に実行される原因となった bug を修正した`
   - OK: `bug を修正した。この bug は昨夜の deploy で発生し、retry 処理を二重に実行していた`

出典: 本多勝一『日本語の作文技術』/ 文化庁「公用文作成の考え方」(2022) / 木下是雄『理科系の作文技術』(逆茂木型)。

## 同一助詞の連続回避

同じ助詞 (「の」「に」「も」「て」) が続いて係り先を誤読する場合は、動詞化か語順変更で直す。出現回数だけでは書き換えない。

- NG: `本年の当課の取組の中心は AI 導入だ`
- OK: `本年、当課が中心的に取り組んでいるのは AI 導入だ`

出典: 文化庁「公用文作成の考え方」/ textlint-rule-no-doubled-joshi。

## 受身は主体が書けるなら能動で書く

受身 (`〜される` / `〜られる`) をむやみに使わない。動作の主体を書けるなら能動で書く。受身によって主体が曖昧になる場合だけ直す。

- NG: `検証が実施され、問題が確認され、修正が行われた`
- OK: `test で検証して問題を 2 件見つけ、修正した`

例外 (UI 操作説明): 読み手の操作は能動 (`[保存] を押す`)、システム側の結果は受動 (`データが保存される`) で書き分け、態そのもので主体を示す。

出典: 文化庁「公用文作成の考え方」/ 木下是雄『理科系の作文技術』/ SmartHR Design System。

## ら抜き言葉禁止

ら抜き (見れる / 食べれる / 来れる) を使わない。可能の意味は「〜できる」への言い換えが最も明確になる。

- NG: `この画面から log が見れる`
- OK: `この画面で log を確認できる`

出典: textlint-rule-no-dropping-the-ra。

## 漢語の連結を開く

漢語が連なって名詞同士の関係を読めない場合は、助詞を補うか動詞に開く。固有名詞・技術用語は対象外とし、文字数だけでは直さない。

| Before (連続漢字) | After (助詞挿入 / 訓読み開く / 動詞化) |
|---|---|
| `利用者認証処理管理` | `利用者の認証処理を管理` |
| `構造的変化傾向分析` | `構造的な変化傾向の分析` |
| `段階的強化` | `段階的に強化` |
| `逐次化検出` | `逐次に並ぶ状態を検出` |
| `絶対禁止徹底` | `禁止を徹底する` |

出典: textlint-rule-preset-ja-technical-writing (max-kanji-continuous-len rule)。

## ひらく漢字 7 品詞 (ひらがな表記推奨)

外向き prose では下記 7 品詞をひらがな表記する。記者ハンドブック (共同通信社) 業界標準に準拠。具体物・物体・時刻そのもの等の本来の意味で使う場合は漢字維持、抽象・概念・形式語の場合のみひらく。

| 品詞 | NG (とじる) → OK (ひらく) |
|---|---|
| 形式名詞 | する事 → すること / する時 → するとき (場合の意) / する為 → するため / する上で → するうえで / の様 → のよう / の通り → のとおり / する所 → するところ |
| 副詞 | 既に → すでに / 例えば → たとえば / 是非 → ぜひ / 沢山 → たくさん / 全て → すべて / 様々 → さまざま / 暫く → しばらく / 大分 → だいぶ / 恐らく → おそらく / 色々 → いろいろ |
| 接続詞 | 又 → また / 及び → および / 但し → ただし / 更に → さらに / 従って → したがって / 即ち → すなわち / 並びに → ならびに |
| 補助動詞・補助形容詞 | 〜て見る → 〜てみる / 〜て頂く → 〜ていただく / 〜て下さい → 〜てください / 〜て居る → 〜ている / 〜て来る → 〜てくる / 〜たく無い → 〜たくない / 〜て欲しい → 〜てほしい |
| 副助詞 | 等 → など / 迄 → まで / 程 → ほど / 位 → くらい |
| 連体詞 | 色んな → いろんな / 所謂 → いわゆる |
| 敬語表現 | 致します → いたします / 頂く → いただく / 下さい → ください |

判定 trick: 「手書きでもこの漢字を用いるか?」を自問する。PC は無自覚に変換するため、用いないなら開く。具体物 vs 抽象概念で迷ったら、抽象側はひらく。

機械での完全な自動化は困難なため (品詞の解析が必要となる)、書き手は「ひらく漢字 7 品詞」表を sweep 基準として参照する。

出典: 共同通信社『記者ハンドブック 第 14 版』 (2022)、各種 Web ライティング規約 (テクニカルライティング業界共通)。

## 冗長表現の圧縮

| Before (冗長) | After (圧縮) |
|---|---|
| 〜することができる | 〜できる |
| 〜を行う | 〜する |
| 〜であると言えます | 〜である |
| 〜ということになる | 〜となる |
| 〜することが可能 | 〜できる |

出典: textlint-rule-ja-no-redundant-expression。

## 弱い表現の禁止 (技術文書本文)

技術文書 (DD / RCA / 報告書) の本文で曖昧語を使わない。断定できないなら「検証が必要」「未確認」と明示する。

| 禁止語 | 置換 |
|---|---|
| 〜かもしれない | 検証が必要 / 仮定: 〜 |
| 〜と思います | 〜と判断する / 未確認 |
| 〜と思われる | 〜と推定する (根拠を併記) |
| 〜可能性がある | 条件: 〜 / 発生率 X% |

既存の「断定語 warn-only」とは逆方向 — 断定語は過剰断定の抑制、弱い表現禁止は曖昧の排除。両方を併用する。出典: textlint-rule-ja-no-weak-phrase。

## 理由・目的の文は「ため」で結ぶ

判断や仕様の理由・目的を述べる文 (特に理由を示す sub-bullet) は、末尾を「〜ため」で結んで主張との関係を明示する。言い切りで終えると、理由なのか追加の主張なのか読み手が判別できない。

| Before (関係が不明) | After |
|---|---|
| 特例で処理を続行するとエラーにならず、この不整合に気付けなくなる | 特例で処理を続行するとエラーにならず、この不整合に気付けなくなるため |

出典: user feedback 2026-08-13 (DesignDoc 推敲)。

## 逆接「が」の連続禁止

1 文中に逆接の「〜が、〜が」が複数回出ない。逆接でない順接の「が」も連続で使わない (文の連結器として濫用しない)。出典: textlint-rule-no-doubled-conjunctive-particle-ga。

## `! ?` は意味と宛先で判断する

PR / DD / RCA / commit message では通常不要だが、引用、UI 文言、実際の問いを表す場合まで機械的に削除しない。語調を変えるためだけに追加・削除しない。出典: textlint-rule-preset-ja-technical-writing。

## 漢数字 / 算用数字の使い分け

- 算用数字: 数量・数えられるもの (`3 件` / `10 人` / `5 GB`)
- 漢数字: 熟語・慣用表現・概数・副詞 (`三位一体` / `数十年` / `一日中`)

混在は同一文書内で統一する。4 桁以上の数値は 3 桁ごとに半角カンマで区切る (`1,048,576`)。年号・ID・code 内は桁区切りの対象外。出典: 文化庁「公用文作成の考え方」(2022) / JTF 日本語標準スタイルガイド。

## 見出しは内容を示す

heading は、その section で分かることを表す。常体や体言止めへ機械的に統一せず、同じ階層で役割が揃っていれば既存文体に合わせる。出典: textlint-rule-preset-JTF-style 1.1.2。

## 全角かっこ前後にスペースを置かない

- NG: `(例) 〜` / `〜 (補足) です`
- OK: `（例）〜` / `〜（補足）です`

英数字前後の半角 space rule と独立 (英数字には space あり、全角かっこには space なし)。出典: JTF-style 3.3。
