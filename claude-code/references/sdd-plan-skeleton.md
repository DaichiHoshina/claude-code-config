# 作業計画書の骨格 (repo に template が無いときだけ使う)

`/sdd-plan` Step 1 で repo の作業計画書 template が見つからなかったときに、この節構成で書く。repo に template があるときはそちらの節構成に合わせ、この file は使わない。

```markdown
# 作業計画書: [機能名]

## 関連ドキュメント
- Design Doc: [path または 未作成]

## 目的

## 目的と実装の対応 (Phase が 3 つ以上のときだけ、`references/purpose-traceability.md` に従う)

## 影響範囲
### Change Map (構造の中の変更境界。`| 層 | 名前 | 責務 | 変更 |` の表。Clean Architecture の内側の層から上に並べる。変更しない層も行にし、変更する層の `変更` 列に `★ PR #n` を書く)
### 既存実装の確認 (Design Doc が無い 1 文の要件のときだけ書く)
### 対象ファイル / ディレクトリ (層と責務。file path は `/sdd-phase-design` へ送る)
### テスト対象
### Design Doc との差分

## 処理フロー
[主要な操作ごとに番号付きの手順。今回の変更で挙動が変わる手順の先頭に `★` を付け、末尾に担当 PR を添える (例: `★ サイズを選択する — PR #3 で発送依頼の transaction の内側へ移動する`)。印の無い手順は変わらない]

## PR 分割計画
- flag: [使わない (理由: 1 文) / <flag 名> (配線 PR で OFF、有効化 PR で ON)]
### 計画外の PR (実装中に見つかる不具合 / 既存の欠け / review 後の見た目調整。目安は実装 PR の 3 割)
### PR #1: [Phase 名]

- 依存: なし
- branch: [...]
- 既存挙動: 変わらない
- 想定変更行数: [N] (根拠: [近い実績 × 変更面の比を 1 行])
**対象**: [層と責務。file path は書かない]
**Read/Write**: [責務 1 行で列挙]
**対象外**:
**完了条件**:
**実装への指針**: [完成形を変えない決定 + Step 2.5 で引き当てた rule]
#### 目的
#### タスク (責務の単位。file:line / method 名 / TODO comment 位置は `/sdd-phase-design` が決める)
#### 動作確認手順

### PR #2: [Phase 名]
(PR #1 と同じ構成。既存挙動は「変わる (<flag> ON のとき)」の形で記載する)

### マージ順序と依存関係
```
