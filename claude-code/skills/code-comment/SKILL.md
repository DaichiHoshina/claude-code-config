# code-comment — コードコメント品質チェック & リライト

Goal: code に対するコメントを 「Why not (採らなかった選択肢と理由) 中心・最小限」「コードから読める / 調べれば分かる内容を記録しない」「AI 時代の Comment Traps を避ける」 に合わせる。この skill は判定基準を `guidelines/writing/code-comment.md` canonical を唯一の source of truth として参照する (この skill は list を保持しない)。書き直しでは `guidelines/writing/PRINCIPLES.md` の「文章生成の不変条件」を優先し、code や既存コメントから確認できない設計理由を作らない。

## Activation criteria

trigger 語 (skill auto-fire):
- 「コメント書いて / 追加して」「godoc 書いて」「docstring 書いて」「JSDoc 書いて」
- 「コメントレビューして / 整理して」「コメント audit」「Comment Traps」
- code file 編集中に `// ` `# ` `-- ` `/* ` `<!-- ` を新規追加する場合
- 既存コメントの Why not 不足 / what 重複 / 擬人化 を指摘・修正する場合

**skill 非発火時も同 rule を適用する**: chat inline での code 生成 / Edit tool 直接呼びの場合も、canonical `guidelines/writing/code-comment.md` の 4 rule (default 書かない / 主語で置き場を決めてから該当行の真上 / 見ればわかる what は削除 / 関数本体 1 行目の comment は godoc 候補として見直す) を守る。skill 起動が overhead になる小規模編集で rule を落とさないための保険で、判定基準は canonical 単一 SoT のまま。

非対象:
- PR 本文 / commit message (`guidelines/writing/pr-description.md` + `commit-message.md` 担当)
- 散文 docs / RCA / postmortem (`guidelines/writing/long-form-doc.md` 担当)
- 日本語可読性のみ (`/jp-fix` 担当)

## Startup behavior

1. **canonical 参照** (`guidelines/writing/code-comment.md`) を Read してから判定する。この skill は判定基準を保持しない
2. ターゲット解決 (never ask back):
   - ARGUMENTS に file path → 該当 file のコメント抽出
   - ARGUMENTS 空 → 直前 assistant turn の code block 内コメント
   - どちらもなし → 「対象 file 指定 or コメント貼り付け」と 1 行返す
3. 抽出後、canonical の監査カテゴリ table で **1 コメントずつ分類**
4. review 依頼では根拠付きの finding と必要な修正文を出す。修正依頼では file を直接直し、最終報告に分類工程や全件の Before / After を並べない
5. 読み違い、設計理由の欠落、実装との乖離がない既存コメントは、表現の好みだけを理由に書き換えない。再点検でも新しい変更を必須にしない

## Decision flow (canonical 3 分類 + 削除カテゴリ)

`guidelines/writing/code-comment.md` の構造に従う:

| 判定 | 対応 |
|---|---|
| **保持する 3 分類** (Why not / 調べても見つけにくい外部 memo / 公開 API の godoc) | そのまま、または日本語品質のみ rewrite (長くなるなら削除を先に検討) |
| **WHY (設計根拠)** | commit log へ移動してコードからは削除 |
| **削除カテゴリ + AI marker** (what / PR 文脈依存 / 自明 / defensive / 主観評価 / テスト不確実 / 重複 / 経過メモ / commented-out / 他宣言参照だけ / grep で分かる情報 / AI marker) | 該当行を削除 (書き直しより削除優先) |

詳細判定基準・例・category table は **canonical を直接 Read** する。この skill 内で list を再記載しない (重複は drift 源)。

**行数は指摘対象外**: canonical は行数上限を設けない。「上限 N 行超過」等の行数を根拠にした指摘は誤引用として discard する。

**新規 comment には名詞句 self-check を必ず当てる**: canonical 「状況を自作の名詞句に縮めない」の手順で、書き手が状況を短い名詞句 (「有効行 0 件化」「誤同梱」等) に縮めていないかを見る。該当したら意味と目的を文に開く。review で「これはどういう意味?」と問われる comment の主因になる。2026-08-24 集計では DesignDoc 略語より件数が多い。

## AI 時代の 2 強化観点

必ず審査する 2 論点 (詳細は canonical `guidelines/writing/code-comment.md` 「AI 時代のコメント」section を参照):

1. **AI 生成マーカー禁止**: `// AI-generated` / `// Generated by Copilot` 等を検出して削除
2. **Comment Traps 回避**: commented-out code / 実装と乖離したコメントを検出して削除または同 PR で更新

## Output format

review 時は、対象・判定・修正案を簡潔に出す。修正時は成果を直接述べ、変更があればコメント全体に関わる要点を 1 文で返す。変更が不要なら「読み違いにつながる問題は見つからなかった」とだけ返す。個々の言い換え、触らなかったコメント、分類工程、成功した検証、全体評価、今後の改善案は返さない。失敗や未解決の問題は省かない。user が分類理由を求めた場合だけ Before / After を示す。

````
## 抽出 (N 件)
1. path:L12  `// i をインクリメントする`  (what)

## 判定

### 1. what (削除)
Before:
```go
// i をインクリメントする
i++
```
After: (削除)
````

分類は数値化しない。該当コメントと canonical の分類条件を対応付けられない判定は **discard** し、迷う場合は断定せず確認事項として出す。

## 非対象 (誤発火を避ける)

- 言語別 syntax の細部 (godoc 仕様 / JSDoc tag) → 言語公式 docs 参照
- 仕様コメント自動生成 → code・仕様・issue から理由を確認できる場合だけ書く。理由が無ければ作らず、必要なら user に 1 点確認する
- 1 行 typo 修正 → skill 起動せず inline Edit
