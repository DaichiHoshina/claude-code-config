# PR本文 + レビュー応答

> **Purpose**: PR body とレビューコメント応答の書き方規範 (構造・NG 項目・添字運用)。

## レビューコメント添字 (推奨)

| 添字 | 意味 |
|---|---|
| `must` | 修正必須 |
| `imo` | 任意・意見 |
| `nits` | 細かい指摘 |
| `q` | 質問 |

プロジェクト規約が存在しない場合の汎用 default として使う (プロジェクト規約が違えばそちらに従う)。

## 既定形 (全 repo 共通、user 決定 2026-09-03)

PR body は次の 3 点を default にする。他の節はこの既定形を前提に読む。

- **抽象的な日本語の説明で書く**: 何が変わり、読み手に何が起きるかを現象で書く。識別子や実装詳細は、変更範囲の特定に必要なものだけ記載する
- **本文全体を箇条書き + インデントで書く**: 上位の項目が変更 1 文、下位の項目が理由や補足。散文の段落は置かない (設計判断の説明で箇条書きだと因果が失われる場合だけ短い段落を許す)
- **なるべくミニマルにする**: 該当する section だけ残し、1 項目 = 1 論点で自明な変更は数項目で終える。背景や構造を追加して水増ししない

## 文の形 (user が書き直した形、2026-09-18)

AI が書いた body 4 本を user が全文書き直した差分から取った。既定形の 3 点に加えて、次の形で書く。

- **1 文ごとに改行する**: 背景のように 2 文が続く節では、文の切れ目で改行する。1 行に詰めない
- **括弧の補足は理由の形で閉じる**: 「(WHERE に置くと一覧から消える)」でなく「(〜消えるため)」。補足が根拠であることを文末で示す
- **確認してほしい項目には必ず理由を添える**: 「id の大きい方を返すこと」だけでは、なぜその形が正しいのかレビュワーが判断できない
- **連続する PR の参照は相対表現にする**: 「5 本目の PR で行う」でなく「次の PR で行う」、「7 本目」でなく「最後の PR」。本数を数え直さずに読める。ただし自分の位置を示す「7 本のうち 4 本目」は残す
- **太字は本当に注意が要る 1 行だけに使う**: 例は「番号は暫定の数字で、マージ前に書き換える」。複数箇所を太字にすると強調が効かない
- **diff を読んで確かめられない話は書かない**: 採用しなかった別実装の参照、別 issue との merge 順序、条件を入れなかった箇所の説明は落とす。理由は主たるもの 1 つに絞り、二次的な根拠を並べない

## 節構成は repo の PR template に従う (user 決定 2026-09-18)

**repo に `.github/pull_request_template.md` があれば、その節をそのまま使う**。独自の節を作らない。同じ repo の他の PR と節が揃っていれば、レビュワーは「影響範囲はここ」「動作確認の手順はここ」と当たりを付けて読める。

repo template が無い repo でだけ、下の「テンプレ (repo template が無い場合)」を使う。

### 節への配置

レビュワーが最初に知りたい 3 点 (どこを確認すればよいか / 本番の挙動が変わるか / 連続する PR の何本目か) は、独立した先頭行にせず repo template の該当節へ記載する。

| 伝えたいこと | 配置先 (product repo の template の場合) |
|---|---|
| この PR で確認してほしいこと | `## レビュー観点` のチェックボックス |
| 本番の挙動が変わるか | `## 影響範囲` の 1 行目 |
| 連続する PR の何本目か | `## 背景` の 1 行目、または `## 備考` |
| 変更内容と判断の理由 | `## 実装概要` |
| 確認した内容 | `## 動作確認・エビデンス` |

- 節名は repo template の表記をそのまま使う (`## 動作確認・エビデンス` を `## 動作確認` に縮めない)
- 該当しない節は見出しごと削除する。空節や「特になし」を置かない
- template のチェックボックス (`- [ ] マニュアルテスト実施可否`) と label 記載欄 (`- \`operation check\``) は削除しない

### レビュー観点の書き方

「xxxx」の placeholder を具体的な確認項目に置き換える。1-2 項目に限定し、3 つ以上になるなら PR を分割する候補とする。

```markdown
## レビュー観点

- [ ] 無効化の UPDATE が主キー指定になっていること (当選景品 ID を条件にすると隣接行までロックが広がるため)
- [ ] 取り消しの 3 経路が同じ関数を呼んでいること (経路ごとに書き方が分かれると、次の変更で片方だけ直すため)
```

### 影響範囲の書き方

ユーザー機能単位で、レビュワーが動作を確認する対象を列挙する。挙動が変わらない PR はその旨を明記する。

```markdown
## 影響範囲

- [ ] マニュアルテスト実施可否
- アプリの挙動は変わらない (列を追加するだけで、code はまだ列を読まない)
```

```markdown
## 影響範囲

- [ ] マニュアルテスト実施可否
- 管理画面の発送詳細 (サイズ欄と件数)
- 発送依頼の作成 API
```

### 実装概要の書き方

変更を箇条書きで列挙し、判断の理由は下位の項目に置く。論点が 3 つ以上あって下位の項目では収まらないときだけ `###` の見出しを作成する。

```markdown
## 実装概要

- 取り消しでサイズ選択を物理削除せず、`deleted_at` を記録して行を保持する
  - 削除するとどのサイズを選択して失敗したかを後から確認できない
- 無効化する行の指定に主キーを使う
  - 当選景品 ID を条件にすると、REPEATABLE READ で隣接する範囲までロックが広がり、別の当選景品への登録を待たせる
```

- 見出しを作成する場合は論点の名前 (「〜している理由」「削除した test」) にし、文にしない
- 箇条書きの入れ子は 2 段までにし、3 段目が必要なら見出しに上げる
- 「chain」は自分用の作業語で、外向き text には書かない (user 指示 2026-09-11)。「3 本のうち 1 本目」と書く
- migration の番号は「暫定の数字で、マージ前に書き換える」と書き、採番の経緯は書かない
- 末尾に Claude session の URL を付けない

### 挙動が変わらない PR の印

「影響範囲」に挙動が変わらないと記載する PR は、title に repo の印 (`[確認不要]` 等、repo の慣習に合わせる) を付ける。呼び出し元のない実装、I/F 変更だけ、migration だけ、削除だけ、がこれに当たる。

計測 (2026-09-06、直近 90 日 1,732 PR) で merge 待ちが短い人ほど、この印とレビュー観点の明示で review の範囲を限定していた。

## 本文の書き方

- **開いた文章 (plain JP) 必須**: bullet 内も対象・状態・関係が伝わる形で書く。項目名や結果として意味が完結する名詞句は残し、文体調整のために事実・時制・評価を変えない (canonical: `guidelines/writing/PRINCIPLES.md`)
- **分岐や制約の説明は「状況 → 読み手の結果 → 対処」の順で、対処は識別子で書く**: 上位 bullet が対処 (変更 1 文)、下位 bullet が状況と読み手に見える結果。`不整合時` `このケース` のような書き手のラベルや、`倒す` `流す` の口語圧縮は使わない (canonical: `PRINCIPLES.md` 「状況 → 読み手の結果 → 対処」)
- **簡潔ミニマル**: 該当しない template section は見出しごと削除する。空 section・「特になし」placeholder を記載しない。自明な変更へ背景や構造を追加して水増ししない
- **箇条書きを基本形にする**: 変更の列挙も理由の説明も bullet + インデントで書く。設計判断で bullet だと因果が失われる場合だけ短い段落に戻す (`PRINCIPLES.md` の「判断理由は段落」は PR body では既定形が優先する)
- **階層で関係を表現**: 上位下位・因果・包含関係はインデント / サブbullet。散文で接続詞を重ねない。詳細 pattern と NG/OK 例は `PRINCIPLES.md` `## 箇条書き階層化` `### checkable pattern` 参照
- **構造（場所）で束ねる**: 変更を「ファイル / モジュール / レイヤー」単位でグループ化。**「what / why / how」など抽象観点でsectionを割らない**
- **section重複を避ける**: 同じ事実は1ヶ所のみ。背景・原因・影響範囲で同内容を繰り返さない
- **必要な識別子は書く**: クラス名・設定キー・関数名は変更スコープ明示に必要なら記載OK。逆にdiffから自明な変数名の羅列・実装詳細は省く
- **長さは内容に従う**: 自明な変更は数行、設計判断を含む変更は原因や代替案も記述
- **Web 可読性**: GitHub / GitLab PRは scan 前提。主張型 heading と段落冒頭で要点を追えるようにする — 詳細 `PRINCIPLES.md` `## Web 可読性`

### 変更 bullet の型 (親 = 変更 1 文 / 子 = why / how)

変更を bullet で列挙するときは、上位 bullet を「何を変えたか 1 文」に限定し、その理由 (why) や実装詳細 (how) は下位 bullet (`  - `) に置く。同レベル bullet に「変更」と「変更の理由」を並列に置かない (階層構造が消えて読み手が結論と根拠を区別できなくなる)。

OK:

```markdown
- 親商品の識別子を writer で NULL にする。
  - `has_variant=true` のとき、親の `items` 側の識別子を NULL にする。
  - svc 側に置くと usecase ごとに同じ判定を実装するため、writer に置いた。
- `svc/admin/item_variant_code` に get を 1 本追加する。
  - 親商品 ID から variant 行一覧を返す。
  - create / update / delete は後段の別 PR で入れる。
```

NG (平坦・結論と根拠が並列):

```markdown
- 親商品の識別子を writer で NULL にする
- has_variant=true のとき、親の items 側の識別子を NULL にする
- このルールを svc に置くと usecase ごとに同じ判定が必要になるので、writer に置く
- svc/admin/item_variant_code に get を追加する
- 親商品 ID から variant 行一覧を返す get を 1 本追加する
```

### 時限マーカー禁止 (merge 後に意味を失う表現)

PR body / commit / issue に、merge 後や数か月後の読み手が解決できない時限参照を含めない。canonical: `PRINCIPLES.md` `## 避けるパターン` 「時限的マーカー」行。

- NG: `<domain> 4/7 [<project>] variant マスタの admin GET endpoint を公開する (#30472) #36362 以降`
- NG: 「この PR で新設」「先週合意した通り」「直近の incident で」
- OK: 「後段 PR」「後続の chain」「別 PR で追加する」など、具体番号を含まない時制中立表現に書き換える。参照 PR / issue が必須なら `#36362` 単体で書き、「以降」「これから」などの時制語を付けない
- 例外: `Closes #XXX` の関連付け行、`Depends on #XXX` の依存関係行は維持する (書式が確立していて時制語ではない)

## PR body の抽象度と行数

実装詳細 (属性名 / 内部関数の分岐 / 型の内訳 / lib の内部経路 / 段数・件数などの数値) を並べず、抽象度を 1 段上げて「何が起きたか / なぜそれが起きたか / どう直したか」の現象記述で書く。

### 抽象度の線引き

- **記載する**: 現象レベルの原因 (例「差し替え処理が画面を描く処理を止めていた」) / 数値 (396 回 / 12.6 秒) / 対象画面 / 修正の 3 点要約 / 見送り理由
- **削る**: 属性名の混在経路説明 / 型の派生 / file 発見性の話 / 「新 file 作らず既存に統合した」等の些末な設計選択
- **技術的な根拠は見出しに分ける**: SQL・DDL の句 (`ALGORITHM=INSTANT` 等) / lock の挙動 のような、読み手が判断に使う根拠は削除しない。`## 実装概要` の下に論点ごとの `###` (判断 1 文を見出しにする)、DDL の指定など下位の区分があれば `####` を置き、その中に理由を箇条書きで書く。入れ子を 3 段にしない (user 指示 2026-09-11、PR #39868: 「箇条書きじゃなくて ### #### を使って」)。上位に詳細を混ぜると「ミニマルに」と直され、詳細を削除すると「理由も書いて」と直される
- **error 番号は日本語の説明に置き換える**: `Error 1845` `SQLSTATE 23000` `exit 137` のような番号は、読み手が調べないと意味が分からない。何が起きるかを日本語で書き、番号が必要なら括弧で添える (user 指示 2026-09-18)
  - NG: 「index が残ったまま列を削除すると Error 1845 になる」
  - OK: 「index が付いた列は定義変更だけの削除ができないので、index の削除と同じ文で実行する」
  - 番号を添える場合: 「〜ができない (MySQL の Error 1845)」のように、日本語の説明の後ろに置く
- **追記を頼まれたら見出しを 1 つ増やす**: user が「この理由も body に書いて」と言ったら、`## 補足` の中に `###` を 1 つ追加してその下に bullet で記載する。既存 bullet の文を長くしない
- **判断基準**: **「diff / git log / 対象 file を読めば分かる」なら削る**。「diff からは読み取れない現象・意図・代替案」だけ記載する

### 分量の判断

- 行数で上限や不足を判定しない。レビュアーが判断に使わない実装経緯や重複説明を削る
- 設計判断がある場合は、採用理由と見送った案を、判断できる範囲で記載する
- 手順や備考は、別の目的や論点が混在している場合だけ分ける

### 削らないもの

- template 必須の checkbox (「マニュアルテスト実施可否」等の repo 固定要素)
- 影響範囲の対象画面 list
- 動作確認・エビデンスの placeholder (後追い検証用)
- ラベル記載欄 (`operation check` 等)

## 設計を採用した理由 section (設計判断を含む PR で推奨)

設計判断を含む PR は「設計を採用した理由」section を置き、論点ごとに採用案と却下理由をつなぐ。文数は揃えない。

## 残論点 (Open questions) の書き方

残論点を PR へ記載するときは、レビュアーへの依頼が「調査」でなく「意思決定」になる形に整える。

- 各案に利点と代償を 1 行ずつ添える
- 実装者の推奨を 1 つ明記し、理由を 1 行で書く
- 推奨を 1 つに限定できない論点は、PR へ記載する前に検証して解消するか、拮抗している旨と判断材料を記載する

OK: 「cache TTL は 60s (推奨) か 300s か。60s は鮮度優先で hit 率が下がり、300s は逆。書込頻度が高い画面のため 60s を推す」

## テンプレ (repo template が無い場合)

repo に `.github/pull_request_template.md` が無いときだけ、この節構成を使う。ある repo では repo template に従う (canonical: 「節構成は repo の PR template に従う」)。

```
## 背景
## Related Issue
## 実装概要
## 影響範囲
## 動作確認エビデンス
## 動作確認手順
## 備考
```

- テンプレは上限であって必須構成ではない。該当する section だけ記載する (小変更なら 背景 / 実装概要 / 動作確認 の 3 section で十分)
- 関連Issueは必ず対応付け (`Closes #XXX`)。1 つの Issue を複数 PR に分割する場合は、途中の PR は `ref: #XXX` に留め、最後の 1 本にだけ `closes` を記載する
- 別repoのIssueは `org/repo#XXX` 形式

## 禁止

- 「Generated with X」「AIが生成」等のフッター
- 「Cursor 指摘反映」「Claude が生成」等の AI / tool 名の本文言及。commit trailer の Co-Authored-By も付けない (user 指示 2026-08-03、canonical: `commit-message.md`)。修正理由は事実 (「発見性が高い」「既存 helper とまとめた方が自然」等) に言い換える
- テーブル形式のファイル一覧 (diffで読める)
- 過剰絵文字・絵文字主体のsectionヘッダ
- commit message の貼付け直し (`git log` で読める。本文は背景・影響・検証に集中)
- **経過メモ (時系列の変遷記述)**: 「当初 X で実装したが Y に変更」「レビュー指摘で Z に修正」等の開発中の変遷は書かない。PR body は**現在の diff の事実のみ**を記述する (最終形の背景 / 影響 / 検証)。変遷は commit history とレビュースレッドが保持する。設計を途中で変えた理由が読み手に必要な場合のみ、「Z を採用した。X は〜のため不採用」と**現在形の採用理由**として 1-2 行で書く

## レビュー応答 (PR修正時)

| ルール | 詳細 |
|---|---|
| Resolve主体 | **レビュワー** がresolveにする。実装者は基本resolveしない |
| 修正リンク | コメントへの修正対応には必ず**修正コミットのリンク**も添付 |
| commit粒度 | **1コメント = 1 commit** で整理 (force-push可)。textlint / lint修正単独commitは作らず対応commitに合流 |
| 返信例コピー | ユーザーが返信例を要求した場合、生成 + クリップボードコピーまで |

### 返信 comment の書き方 (5 パターン)

AI が代筆する返信 comment は、author が数日後にスレッドを見返して意味が取れる形にする。commit で対応した事実を並べるだけでは足りない。

- **経過メモ削除**: 「〜わかりにくかったので godoc に追記した」「〜だったので直した」の書き手視点の経緯は削り、現在の code の事実だけ書く (code-comment.md「(8) 経過メモ」と同判定)
- **答え先出し**: 質問が Yes/No なら 1 文目で Yes/No を返す (例「統一されているか?」→「統一されていなかったので直した」)
- **file 名付き行番号**: `l91` `l93` 単独で書かず、`product_size_code_test.go:91` のように file 名を必ず付ける。同 PR 内でも scroll 位置の共有はできない
- **前提共有 1 行**: 別 PR で入れた変更 / 言語仕様 / 社内 helper の存在等、author が数日後に忘れる可能性があるものは 1 行追加する (例「Go は同 package で同名関数を 2 つ持てないので」)
- **「〜済」で締めない**: `guidelines/writing/PRINCIPLES.md` の常体規範を返信にも適用。「対応済み」「反映済み」で切らず、事実で締める
- **commit hash は根拠として最後**: 「〜に直した (`abc1234`)」の形。「commit メッセージ参照」で誘導せず、返信内で意味が閉じるようにする
- **対処は識別子で、状況と結果は具体名で**: 1 文目に「`Label` を空で返すようにした」のように何をどうしたかを識別子で書き、2 文目に「hidden のときは画面がサイズ欄を出さないので」と状況と読み手の結果を添える。`表示側で吸収した` `不整合時は倒した` のような抽象主語と口語圧縮は使わない (canonical: `PRINCIPLES.md` 「状況 → 読み手の結果 → 対処」)

NG → OK 例:

| NG | OK |
|---|---|
| 「用途が読み取れなかった件は godoc に追記した」 | 「godoc にもその流れを書いた」 |
| 「この PR 内で慣習にそろえるところまで対応済み」 | (削除。「〜に直した (`761cc8d`)」で締める) |
| 「同 package に新 file (l91) を追加した」 | 「この PR で同 package に `foo_test.go` を追加した。そちらの l91 に〜」 |

## PR body 追記ルール

- **後付け H2を並べない**: 「追加対策」「最新ステータス」等の時系列追記は既存セクションに統合する
- **箇条書きは 1 行に結論**: 詳細値 (commit hash / 関数名 / 数値) は同行内 `()` に添える (`- キャッシュ TTL を 60s に短縮 (修正: a1b2c3d, 関数: `setCacheTTL`)`)
- **「補足」「最新ステータス」の位置**: CodeRabbit Summaryの前に置く (auto-gen 領域の後ろは読まれない)

## 動作確認セクションの構成

- **test の話は記載しない** (user 指摘 2026-09-18、複数回)。test 関数名、subtest の件数、test で確かめた旨、mutation check の手順、lint と build の結果はすべて対象外とする。CI が実行して結果を表示するので、本文に転記しても reviewer の判断は変わらない。記載するのは**製品を動かして観察した結果**だけで、画面の表示、API の応答、DB の行の状態が該当する
- **実機で確認していないなら、確認する項目を未チェックのチェックボックスで記載する**。test が通ったことを動作確認の代わりに記載しない。未実施だと分かる形にして、実施後にエビデンスを追記する
- **1セクションに統合**: 同種の検証を `## 動作確認` 1セクションに集約し、`### ローカル` / `### dev リハーサル` / `### 負荷試験` の小見出しで時系列分離する
- **並列に何本も生やさない**: 検証セクションを `## 動作確認 (ローカル)` / `## 動作確認 (dev)` のように H2 並列で並べると、後付け H2と区別がつかなくなる
- **時系列追記は既存小見出しに統合**: 「再検証」「追加検証」等を新規H3で並べず、既存小見出しに統合する
- **手順は 3 項目上限**: scan 前提で 4 項目以上に膨らむと読まれない。超過分は別 doc / dashboard URL / log 共有 link に置き、PR 本文には要約 + 参照のみ記載する
- **スクショに撮影用の要素を含めない**: alert のように画面に残存しない通知は、保存後の画面と API の応答 (status / body) をテキストで併記する。文言を DOM に描いて撮ると製品に無い見た目になり、成功とエラーの区別も付かない

## 外部共有不可 path / URLを貼らない

- **ローカル絶対 pathは貼らない**: `/Users/<name>/...` 等の絶対 pathは repo 外の読み手が解決できない
- **gitignored / 外部不可視 pathは貼らない**: `.local/` / 個人 dir 配下 fileの pathは PR reviewerが開けない
- **必要な内容は本文に書き起こす**: 外部共有可能な場所 (Notion 共有page / dashboard URL / PR 本文直書き) に転載する
- **path を記載する時の判定基準**: 「reviewerがcloneした repo 内で解決可能か」を確認する。Noなら本文展開 or 共有可能 URLに置き換え

## レビュアー視点のチェック

- 1つのsectionに同じ事実が重複して現れていないか
- 「ファイル単位」と「観点単位」のsectionが混在していないか
- 動作確認手順を見て、第三者が再現できるか

## chain PR 情報の末尾フォーマット

PR chain (stacked PR) の上流と後続の関係は body 末尾に 1 行で固定する。

```
chain: <前 PR (merged なら明記)> ← この PR (N/M) → <次 PR>
ref: <DD の URL / issue リンク>
Related: #<issue>
```

- 前 PR が merged 済みなら `#XXXX (merged)` と明記する。base が `main` になるだけだと 1/M・2/M の存在が読み取れない
- 最終 PR は `→ 次 PR` を省略し `(9/9、最終)` と表記する

## doc / コメント追加は実装概要に書かない

- godoc / code comment の追加や修正は PR body の実装概要に書かない。レビュー対象は diff、概要は「何を動かすように直したか」で書く
- doc 更新が主目的の PR (例: README 更新のみ) は例外
- 2026-07-17 の PR #37142 で「reader に godoc を追加する」bullet が概要に含まれ、user 指示で削除された経緯がある
