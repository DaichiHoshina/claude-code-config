# DesignDoc作成プロトコル

DD = DesignDoc。共通文章原則は [PRINCIPLES.md](PRINCIPLES.md) 参照。

## 前提: DDと詳細設計書は別物

混同するとレビュー不能になる。**書く前にWhyかHowかを判別する**。

| 項目 | Design Doc | 詳細設計書 |
|------|-----------|-----------|
| 主目的 | 設計判断の共有 | 実装仕様の定義 |
| 主読者 | エンジニア全体 / レビュアー / SRE / PdM | 実装者 |
| フォーカス | **Why / Architecture** | **How / Implementation** |
| 内容 | 背景・課題・選定理由・トレードオフ・非機能要件 | テーブル定義・API・SQL・バリデーション・シーケンス |
| 例 | 「なぜSKIP LOCKEDを使うか」 | 「SQLをどう書くか」 |

**DDD / マイクロサービス領域ではDD力 > 詳細設計力**。transaction / lock / idempotency / saga等は「実装」より「設計判断」が価値。

## DDの6要素 (フル版は全部、軽量版は該当分のみ)

テンプレは選択制 (軽量版 5 節 / フル版 12 セクション、後述「テンプレ選択」)。フル版では 6 要素を全て書く。軽量版では Why と失敗ケースを必須とし、残りは変更内容に該当する要素だけを Appendix 等で扱う (例: DB 変更がなければ移行戦略は不要)。

| # | 要素 | 内容 |
|---|---|---|
| 1 | **Why** | PRD / 要件との接続 (×「新テーブル作る」○「O(1) 抽選のため新テーブル作る」) |
| 2 | **比較とトレードオフ** | Alternatives必須、最低2案。設計は正解でなく選択 |
| 3 | **変更耐性** | 「今動く」でなく「変更しやすいか」 |
| 4 | **責務境界** | service / module間の役割 (DDD的、曖昧だと事故る) |
| 5 | **失敗ケース** | 在庫不足・API失敗・二重実行・冪等性など本番で死ぬ点 |
| 6 | **移行戦略** | DB変更はExpand → Migrate → Contractの3段 |

レベル高い書き方: 数字で語る (O(n)→O(1)) / 図で説明 (シーケンス・ER・アーキ) / 制約明示 (MySQL 8.4 LTS、READ COMMITTED)。

## DDと runbook / 実装 docsの役割分担

DDは **方針** を扱い、**具体閾値・実装値・運用手順** は別 doc (runbook / 監視設定 / 実装コメント) に委譲する。

| 種別 | 扱う内容 | 例 |
|---|---|---|
| DD | 段階分け / 監視意図 / 設計判断 / トレードオフ | 「監視は 3 段階 (当日 / 観察 / 運用)」「なぜこの metricを取るか」 |
| runbook / 監視 doc | 具体閾値 / 通知先 / 対応手順 | 「CPU 80% で alert、Slack 通知先は opsチャンネル」 |
| 実装コメント | 時系列の制約 / API 仕様 / 値の根拠 | 「timeout=2sは p99 + 余裕」 |

**重複検知**: 同じ事象がDDと runbookで具体値含め説明されていたら、DD 側を方針記述に縮め、runbookへリンクで委譲する。DD 内で「具体値は <runbook 名> 参照」と書く。

**Why**: DDで具体値を記載すると、運用調整で値変更時に DesignDoc も更新しないと食い違う。方針 (Why) と値 (How) を分離すると更新コストが値側だけになる。

**実装の内部構造も DD の外**: どの層がどの順で値を渡すか、既に読み込んだ行を再利用するか、test が期待値をどう定義するかは実装者が決める。DD には「判定に何を入力するか」「いつ決まるか」「何が失敗するか」までを記載する。代替案の比較表も仕様の選択肢で並べ、「読み込み済みを使う vs 読み直す」のような実装の書き方の対比を案として立てない。

**Why**: 実装の書き方は DD の承認後に変わるが、DD 側を更新しないので食い違う。仕様として満たすべきことだけ書けば、実装が変わっても DD は正しいままになる。

## 4 Step

| Step | 概要 | 具体 |
|---|---|---|
| 1. 着手前リサーチ | 既存資産・前提の事前確認 | 5観点 + PRD見出し対応表 |
| 2. 初版必須要素 | テンプレ通りに埋める | テンプレ / 用語定義 / アクターmatrix / 数値4点 / Rollback / 未決 / 監視1:1 / UTC-JST / 環境固有名詞 |
| 3. 完成前3段スキャン | 提出前セルフレビュー | 抽象bullet / 数値根拠 / 用語 → lint実行 |
| 4. レビュー対応 | コメント対応規約 | 1コメ = 1 commit、返信にcommit URL、textlint単独commit禁止 |

### Step 1詳細: 着手前5観点

| 観点 | 確認内容 |
|---|---|
| 既存ダッシュボード | 監視・SLOがすでにあるか |
| フラグ | feature flag / kill switchの有無 |
| 識別子実在 | 想定するID・キー・enumが実在するか |
| DB前提 | テーブル・index・制約・サイズ感 |
| 関連層影響 | API / Worker / Batch / 別serviceへの波及 |

### Step 2詳細: 数値4点セット

「規模・頻度・遅延・コスト」を最低でも記載。記載不可なら「未測定 / 推定 / 仮定値」と明示。

### Step 3詳細: 3段スキャン

1. **抽象bullet**: 「対応する」「整理する」等の動詞だけのbulletを発見 → 具体化
2. **数値**: 「多い」「速い」「遅い」を見つけ → 数値or範囲に
3. **用語**: 初出の専門用語に定義があるか / コードフェンス羅列がないか
4. **評価の独立性**: 「複数チェックがある」=「安全」と判定する前に、各チェックが独立した source / 観点を参照しているか確認する。同一値を 2 経路で参照しているだけなら1チェック扱い

## 本文と Appendix の階層分離

DD の本文 = 方針 / 判断 (レビュアー向け)、詳細表 = Appendix (実装者向け) の階層で分離する。

- **本文に記載する**: 設計判断 (Tradeoffs の比較表)、Schema (テーブル構造)、Invariants (守るべき不変条件)、Rollback、移行段取り。**レビューの核**
- **Appendix へ移動する**: Endpoints 全パス表 / Error Handling 全 status 表 / レスポンス enum 表 / 列名 ↔ UI 対応。**実装時に参照する詳細**
- API Design 節は「方針」と「status code の使い分け」だけ書き、一覧は「Appendix を参照」と誘導する

**Why**: レビュアーは「何を・なぜ (設計の意図・判断)」を読みたい。エンドポイント全パス・エラー status 全行・enum 表・file:line・request 構造体を本文に並べると、設計の筋が詳細の中で読めない。

## 散文から実装識別子を除外する (技術用語ちゃんぽん回避)

散文 (Overview / Data Flow / Invariants の説明 / User UI / Admin UI) では、`.vue` file 名 / status code 番号 / table literal / API path を**書かない**。代わりに和名で書き、識別子 ↔ 和名の対応を Glossary に 1 箇所集約する。

識別子を **literal として必要な場所** (Schema 定義 / Endpoints 表 / Error Handling 表 / Mermaid / 実装場所の指示 `svc/...`) には維持する。

**ちゃんぽん (ルー大柴) の回避**: 技術用語 (disable / submit / fallback / rollback / enum / feature flag 等) は literal で維持するが、それを和語に開こうとして「英語 + 和語」を 1 文で併用しない。どちらかに統一する。

- ❌ 「ON → OFF は常に無効にする」(disable を中途半端に和語化)
- ✅ 「ON → OFF は常に操作できない」(地の文は和語で統一)
- ❌ 「未選択 submit を防ぐ」
- ✅ 「未選択の送信を防ぐ」

判定基準: その英語が **識別子 / DB 用語 / API 用語 / 確立した技術語** なら literal でよい。一般動詞 / 一般名詞 (submit → 送信、disable → 無効 / 操作不可) を英語のまま地の文に入れるとちゃんぽん。

### ちゃんぽんでない正当な混在

以下は「技術用語の literal + 日本語の助詞」で正常:

- 「`product_size_codes` への bulk INSERT を同一トランザクションで実行する」
- 「旧形式 fallback で受ける運用に切り替える」

## `<details>` で閉じた Mermaid / 図は self-review 評価対象外

`<details><summary>展開して読む</summary>` で`<details>` で閉じたの Mermaid 図 / コードブロック / 表は、レビュアーが default で閉じた状態を見るため、本文の冗長 / MECE / 負担評価の対象外として扱う。

- self-review (`/jp-fix` / DD レビュー) で行数 / 冗長 / 抽象度を評価する際、`<details>` 配下は集計から除外する
- 露出している (`<details>` に入っていない) Mermaid / 図は通常どおり評価する
- 「図の中身が冗長」は別観点 (図単独の品質) として扱い、self-review で同列に並べない
- `<details>` 化されていない図を見つけた場合は「`<details>` 化を推奨」として提案可

**Why**: `<details>` に入っている時点で「最初に目に入る情報」ではなく、レビュアーが必要時に展開して読む補足扱い。負担計測に含めると過剰指摘になる。

## self-review: 途中経過メタ文を削除

DD を書き終えた時点で以下 4 パターンを grep し、機械的に削除候補に挙げる。

1. **本文 → Appendix への誘導文**
   - 例: 「比較表は Appendix『設計判断の比較』参照」
   - 構造上 Schema Tradeoffs を読んだ後すぐ Appendix が続くなら誘導不要
2. **セクション冒頭の「ここでは X を示す / Y は別途まとめる」型の前置き**
   - 例: 「エンドポイントは Appendix にまとめる。ここでは方針を示す」
   - 次の見出しが「方針」なら冗長
3. **Appendix 冒頭の役割説明**
   - 例: 「実装向けの補足資料を置く。設計の方針は本文側、ここには実装時に参照する具体表を集約する」
   - `<details>` summary に同等文言があるなら削除
4. **見出し直下の概要文 (見出しと同義の繰り返し)**
   - 例: H3「API リファレンス」直下「エンドポイント一覧 / エラーコード対応 / ラベル状態の判定表」
   - 直下の H4 / 表で見える情報なら不要

### 維持してよい例外

- 「本文 X 行で根拠を述べる」のような**読み手の判断に必要な context** (Appendix で技術詳細だけ読むレビュアー向けに前提を 1 行)
- section 内で**暗黙の仮定 / 適用範囲 / out-of-scope の境界**を述べる文 (誘導ではなく内容)

**Why**: レビュアーは目次と見出しで構造を把握するので、本文中の「次は X を参照」「ここでは Y を示す」「実装向け補足を置く」は表示順序から自明な情報の二重通知になる。

## DD 圧縮ルール (雑音を削る)

DD 起草時 / 圧縮 review 時に該当箇所を削る。

削る:

- PRD と重複する背景説明は再掲しない。DD = 設計と運用、PRD = 要件と背景で役割を分ける
- PdM 回答の経緯は別 doc (local-docs 等) に置き、DD には決定事項のみ書く
- Open Questions は「判断が来ないと進めない」未確定論点のみ記載する。確定済 / 回答済の論点は削除する
- Non-Goals は「やらないこと」だけ列挙する。方針説明・既存機能・自明事項は書かない
- Scope は In のみ書き、Out は Non-Goals に集約する (sub-bullet で再掲しない)
- schema 設計は列定義 table (5 列表) に合わせる。DDL 全文は migration 実装者の範疇で DD に貼らない

削らない (判断記録 / 仕様として価値がある):

- Schema Design Tradeoffs (代替案比較 table) / Invariants / Endpoints table / 初出用語の 1 行解説

## spec 型 DD (既定): 実装から逆算して書く

`/design-doc` の既定は spec 型 (`references/design-doc-spec-template.md`)。DD を設計の説明ではなく **実装と検証の入力** として書く (user 決定 2026-09-03)。軽量版 / フル版 / 分割型は、repo の規約や規模で節構成を変えたいときの選択肢で、どれを採用してもこの節の 4 原則は変わらない。

### 逆算の 4 原則

1. **完了の定義から始める**: 「実装が終わった」と言える条件 (受け入れ条件) を先に表で列挙する。ID は振らない (team の DD に ID の慣習が無く、見出しの番号引用は読む人を表へ戻らせる。user 決定 2026-09-05)。PRD の条件は PRD の番号で参照して DD には書き直さず、DD には PRD に無い条件だけを記載する。本文はこの条件を満たすための説明として記述し、どの条件にも対応しない節は削る
2. **実装者が迷う点だけ決める**: データ / API / 画面 / 権限 / 失敗時 / 移行 のうち、実装者が code を読んでも決められない点を「決定事項」に記載する。実装の書き方 (層の分け方 / 関数名 / 読み込み済みの再利用) は含めない (「DDと runbook / 実装 docsの役割分担」)
3. **検証できない仕様は書かない**: 受け入れ条件は「〜のとき、〜が〜になる」の形で、test か手動確認で真偽が判定できる文にする。「適切に」「必要に応じて」を使わない
4. **後段へ渡せる形にする**: `/spec-plan` が受け入れ条件を文の引用で Phase に割り当て、`/spec-dev` が完了報告で満たした条件を返し、`/review --plan` が条件ごとに実装と test の有無を照合する。条件の総数と本文の説明が一致していることを完成前に確かめる

### user が仕様を理解できる文章

読み手は実装者だけでなく、機能を決める user 本人でもある。

- **振る舞いは「誰が / 何をすると / どうなる」で書く**: 主語を user か system の具体名にし、1 文に 1 つの結果だけ書く (例「管理者が在庫を 0 にすると、商品一覧はその商品を表示しない」)
- **識別子を本文から除外する**: table 名 / column 名 / endpoint / class 名は「決定事項」の表と Appendix にまとめ、振る舞いの説明には日本語の名前で書く (「散文から実装識別子を除外する」)
- **用語は初出で開く**: 略語と社内用語は「用語」節で 1 行ずつ定義し、本文では定義した語だけを使う
- **前提 → 結果の順に置く**: 条件が複数あるときは、条件を先に並べてから結果を記載する。例外や境界 (0 件 / 上限 / 同時実行 / 再送) は通常の振る舞いの直後に下位 bullet で置く
- **段落より箇条書き**: 振る舞いと決定事項は bullet + インデントで書き、段落は「設計判断」の採用理由だけに使う

### repo に DD template があるとき

repo に Design Doc の template (例: `.claude/docs/design/template.md`) があれば、節の順序はその template に従う (repo 固有規範が優先)。ただし書くことの無い節は作らない (「該当なし」だけの節は読み手の負担になる。実務 repo の DD 14 本中 0 本が template の節構成をそのまま使っていた、2026-09-05 実測)。spec 型の要素は次の位置に差し込む。

- 受け入れ条件の表と用語: template の最初の節 (概要 / Overview) の直下
- 決定事項の表と設計判断: template で対応する節 (データモデル / API 設計 / 状態管理 等) の冒頭に配置する (条件の番号は添えない)
- 未決事項: template に該当節が無ければ末尾へ追加する。検証の表 (受け入れ条件 / 設計上の対応 / 検証方法) は `--type full` のときだけ書く。spec 型では検証節を置かず、どの test で確かめるかは SPEC の完了条件と `/spec-detail` のテスト観点へ送る (`references/design-doc-spec-template.md`、user 決定 2026-09-05)
- 識別子対応表: Appendix (template に Glossary があればそこ)
- PR 分割と実装順序は DD に記載せず作業計画書に置く。DD の Appendix には作業計画書の path だけを記載する (team の DD で PR 分割を DD に入れた例と入れないと明記した例が割れているため、spec 系の流れでは後者に合わせる)

## テンプレ選択

| パターン | 状況 | 行数目安 |
|---|---|---|
| **spec 型・単ファイル (既定)** | 実装に進める案件全般。受け入れ条件の表を軸に記載する (`references/design-doc-spec-template.md`) | 本文 ≤ 300 (用語表 / Implementation Surface の表 / Appendix / `<details>` は別枠) |
| **軽量・単ファイル** | 小〜中機能、AI生成前提、レビュー負荷下げたい | ≤ 300 |
| **フル・単ファイル** | 大規模変更、セキュリティ影響、複数ドメインにわたる | ≤ 800 |
| **分割型ディレクトリ** | 新サービス立ち上げ・大規模プロジェクト | 各 ≤ 400 |

**迷ったら spec 型から開始** → 設計判断が多く比較や移行の説明が膨らむときだけフル / 分割へ昇格する (昇格しても受け入れ条件の節は維持する)。

### 共通ヘッダー

```markdown
# Design Doc: {タイトル}

Status: {draft | proposed | approved | archived}
Created: YYYY-MM-DD
Issue: {Issue URL}    # あれば
PRD: {PRD URL}        # あれば
```

### 軽量版テンプレ (5節)

```text
## Overview        # 何を実現するか / Issue・PRD リンク (Spec があれば受け入れ条件の対応表を直下に置く)
## Data Flow       # シーケンス図 / 主要フロー
## Data Schema     # テーブル設計 5 列表
## API Design      # エンドポイント表
## Appendix        # 代替案 / 未決事項 / 関連リンク
```

### フル版テンプレ (12セクション)

Overview / Goals & Non-Goals / Background & Spec 対応 / High-Level Design / Detailed Design / Alternatives / Trade-offs / Invariants & Failure Handling / Migration Plan / Rollback / Verification & Observability / Open Questions

#### 初稿に抜けやすい section の補強基準

- Background & Spec 対応: Spec / PRD がある案件では、受け入れ条件を 1 行ずつ「受け入れ条件 / 設計上の対応 / 検証方法」の 3 列表へ書き下す。Spec の内容をここで再説明しない
- Invariants: 常に守るデータ整合性、同時実行と再送で成立させる条件、書き込み時に再検証する条件を分けて書く。失敗時に戻す状態と維持してよい状態を対にする
- Verification & Observability: リリース前の検証とリリース後の監視を別 sub section に分ける。前者は Spec 対応表の各行をどの test で担保するかを書き、後者はログ / メトリクス / アラートの 3 階層で書く
- High-Level Design: Mermaid flowchart を 1 つ以上入れる (ascii は許容、Mermaid 推奨)
- Migration Plan: Expand / Migrate / Contract の 3 段で書く (「3 段階で進める」だけでは不足)
- Rollback Strategy: Phase 別の戻し方 table を書き、無停止 / 部分停止 / 元に戻せない、のどれかを明示する
- Observability: ログ / メトリクス / アラートの 3 階層で書く (ログのみは不足)
- Trade-offs: 「短期影響 vs 長期影響」の軸で書く (例: 短時間の停止を受け入れるか、長期の保守コストを抱えるか)。軸のない pros / cons の羅列は判断材料にならない

### 分割型構成

```text
DesignDocs/{context}/{project}/
├── summary.md       # エントリ、全体像・リンク集
├── architecture.md  ├── domain-model.md  ├── table.md
├── api.md           ├── sequence.md      ├── ui-*.md / batch.md
```

## アンチパターン (ドラフト→最終稿で解消する)

汎用の文章アンチパターン (丁寧口調 / 同内容反復 / 実装詳細貼付 / 余分形容詞 / 中身ないまとめ / PR 文脈依存表現 / 時限マーカー / section 重複) は `PRINCIPLES.md` の `## 避けるパターン (段落・文章全体の構造)` を canonical とする。ここでは DD 固有のアンチパターンのみ挙げる。

| パターン | 対処 |
|---|---|
| 箇条書き3階層以上のネスト | 文章化or 3段まで |
| 自己参照 (「本DD」「実装PRで決める」) | 地の文 / 「実装時に決める」 |
| 実装詳細貼付 (関数順序・ファイルパス・SQL全文) | 「何をしたいか」まで、テーブル名+5列表+index bullet |
| 過去経緯・ドラフト造語 (「当初」「案A」) | 削除、比較は代替案表 |
| WHY欠落の制約 (「分割禁止」だけ) | 「守らないと何が壊れるか」1行 |
| 指示語参照曖昧 / 旧概念残存 / DB方言混同 | テーブル名・列名で一意化、新方式棚卸し、採用DB構文 |
| 既出議論との不整合 | 朝会・チャットの方針を反映、既出案は代替案表 |
| 実装状況マーカー (✅🚧❌) / 番号付き見出し | Statusヘッダー / `##` `###` で十分 |
| 削除残骸文・テンプレラベル残骸 | 最終読み直しで除去 |
| 対策層のラベル造語 (「主対策 / 保険」等) | 実体名で書く (「取り消し処理の修正 / 期限切れバッチの修正」)。層ラベルの定義が本当に必要なときだけ導入 |
| 処理名の省略形 (「取り消し」) | 用語表と同じ完全名 (「取り消し処理」) で統一。省略形は用語ゆれの原因になる |
| 既存不具合の修正を修正内容だけで書く | 「修正前 (本番環境) / 修正後」の対比 bullet で書く。どこからが変更か読み手が判別できるようにする |

## 3 段レビュー (内容 → 文章 → 読みやすさ)

DDレビューは観点が独立した 3 段に分け、**別ループで順に実行する**。1 回で全部見ようとすると観点が混在し、修正後に別観点でやり直しになる。

| 段 | 観点 | チェック対象 | 使うツール |
|---|---|---|---|
| 1 | 内容整合性 (docs) | ファイルパス / 構造体フィールド / DB NOT NULLカラム / PRD 受け入れ条件の対応抜け / Phase 計画の依存 / Why-not 表の妥当性 | `comprehensive-review --focus=docs` / 既存コードgrep |
| 2 | 文章規定 (writing) | 評価語 (重要 / 必須) の根拠併記 / 助詞重複 / だ・である調混入 / AI listing pattern / 抽象語 / 読後アクション末尾明示 | NG 辞書 + リポ textlintをローカル実行 |
| 3 | 読みやすさ (readability) | 情報密度 / 表 vs 段落バランス / 優先度の有無 / 図解の統一 / forward referenceのアンカー化 / 新規読者がスタックする箇所 | AI 目視 + 「初見の PM / 新規engineer 視点」シミュレーション |

**順序が固定の理由**: 内容 → 文 → 構造の順で抽象度が変わる。段 1で内容を修正しても段 2で書き直しが入り、段 2で書き直しても段 3で構造変更が入ると、各段の観点が無効化される。

**運用**:
- `/design-doc` 出力後・PR 起票前に段 1
- PR 起票後・CI 通過後に段 2 (textlint / markdownlintの annotation 確認も含む)
- 段 3 で「初見の読者が読めるか」を確認する
- 各段で修正したらコミット + pushを段ごとに分ける (commitメッセージで段がわかる)

## 読みやすさ改善パターン (段 3で使う)

DDを「初見の PM / 新規engineer / 運営」が読める形にする。1 件直すと連鎖的に他の違和感も消えることが多い。

| パターン | 適用条件 | 効果 |
|---|---|---|
| 用語表を概要より前に置く | 概要内に未定義の専門用語が登場 | 流し読みで意味が取れる |
| 図解の表記を統一する (Mermaidに合わせる) | ASCII artと Mermaid 混在 | 視覚的に分断されない |
| 表のセル長文を要約 1 行に圧縮、詳細を表外段落へ | 表で scanできない | 一覧性と詳細性を両立 |
| 曖昧表現に注釈を追加 (「あり / なし両対応」等) | 専門用語回避で意味が消えた表現 | 「(値が入っていても、空 = NULLでも保存できる)」等 |
| 「最重要の制約」を独立 sectionとして冒頭に | 設計判断の多くの根拠が同じ制約を参照する | 後の表の各セルから参照可 |
| 未決事項に優先度列 + 担当候補列 | 未決事項 5 件以上 | 読み手の次アクションが拡散しない |
| リスク一覧表 (重要度 + 対策難易度) を本文の前に | リスク 3 件以上 | 重要度の差を見せられる |
| リリース計画に依存列 + タイムライン図 | ステップ 4つ以上 | ステップ間の混在期挙動を可視化 |
| forward referenceを全部アンカーリンク化 | 「○○参照」が複数 | 遷移コストゼロ |
| シーケンス図のラベル短縮 | mermaidテキストが視覚的に窮屈になる | 図の可読性向上 |

**Why**: DDは新規読者が「approveするか / 自分の領域を確認するか」を判断する道具。情報を平等に並べると、優先度判断 + 次アクションが拡散する。表 / 図 / アンカー / 優先度の 4 武器で情報階層を作る。

**運用**: 段 3で AIが「初見の PM / 新規engineer / 運営」視点でスタックポイントを 10 個ほど洗い出す → 優先度 高 (構造変更) / 中 (図解差し替え) / 低 (リンク化) に分け、高から直す。

## 反復圧縮パターン (フィードバック別)

DDを「みやすく / 端的に / 抽象度を上げて」と反復で決めていくときに繰り返し有効だったパターン。

| パターン | トリガー | 修正方向 |
|---|---|---|
| 役割ラベル付きbullet | 「わかりづらい」「インデント深い」 | 各 bullet 頭に「確認: / 追加待機: / 上限: / 確定:」等の役割語を付与し構造を平らにする |
| 表 → bullet 化 | 「表だとみづらい」 | **デフォルトは bullet**。表は「5 行以上 かつ 2 軸以上で機械的に対応する」場合のみ採用 |
| bullet → 表化 | 「散文で軸が見えない」 | 状況軸が複数あるなら表で「状況 × 手順」を示す |
| Whyを 1 行添える | 「これはなぜ?」 | 数値や運用ルールの後に **理由 1 行** を sub-bulletで追加。長文化禁止 |
| 単語だけの説明を撤去 | 「単語だけの説明やめて」 | 「比較基準を取得する」→「他シナリオを評価するための比較基準を取得する」等、目的語と動詞を明示 |
| 詳細値を別場所に置く | 「書きすぎでは?」 | しきい値・タイムアウト値等の具体値は未決事項表 / 別 repoに集約、本文は方針のみ |
| 重複・自明削除 | 全体読み直し | 「runtimeで旧方式に戻す手段は持たない」等の自明・前置きを削除 |
| 軸の統一 | 「時間軸 / 状態軸 / 復旧手段軸が混在」 | 軸を 1つに決めて分割、section 名を軸に合わせる |
| 「絶対」確認 | 「絶対に実現できる?」 | 担保条件を明示。「主条件 + 補助条件 + 上限保証」のように multi-layerで書く |
| 抜けの再点検 | 「本当にこれでいい?」 | 直前で書いた選択肢が新セクションで活用されてるか検算 |

**反復順 (フィードバック別)**:

1. 初稿: 思いついた構造で書く
2. 「みやすく」: 表 ↔ bulletの入れ替え + 役割ラベル付与
3. 「端的に」: 詳細値を別場所に移す + 自明削除
4. 「これはなぜ?」: Whyを 1 行sub-bulletで追加
5. 「絶対?」: 担保条件を multi-layerで明記
6. 「本当に?」: 直前で書いた前提・選択肢の活用抜けを点検

**アンチパターン**:

- 表に集約しようとしすぎる → 行数少 / 内容短 は bulletの方が読める。**デフォルトbullet、表は最終手段**
- 「なぜ?」に長文で答える → 1 行sub-bulletを超えたら本文に書きすぎ
- 全 bulletに役割ラベル付与 → 装飾過剰。インデント深い箇所だけ
- フィードバック直後の全体書き直し → 該当箇所だけ局所修正、波及は確認してから

## 図表の型を固定する

| タイプ | 形式 |
|--------|------|
| 処理フロー | mermaid sequenceDiagram (User / API / DBの3-4 actor) |
| アーキ図 | mermaid flowchart (ASCII罫線はNG) |
| テーブル設計 | カラム名 / 型 / NULL / デフォルト / 説明 の5列 |
| インデックス | bullet (主キー → 複合 → UNIQUEの順、各に「なぜ」1行) |
| 不変条件の担い手 (制約を削除または緩める変更で必須) | 何を守るか / 今どの仕組みが守るか / 外す制約が防いでいた場面 / 外した後の担い手 の4列。UNIQUE / FK / NOT NULL / CHECK / 排他制御を削除または緩める diff だけが対象で、通常の DD には要求しない。表が無いと「同等のガードはあるか」「なぜ付けていたか」「どの操作で起きるか」がレビューで 1 つずつ質問される |
| エンドポイント | メソッド / パス / 説明 (必要なら「変更内容」列) |
| 代替案 | 方針 / 採否 / 理由 の3列、採用 ○ / 却下 ×。理由には満たせない受け入れ条件か不変条件を名指しする |
| 受け入れ条件対応 | 受け入れ条件 / 設計上の対応 / 検証方法 の3列。検証方法列は検証 section への索引に留める。`--type full` の Background & Spec 対応で使う形で、spec 型では書かない |
| リリース手順 | 番号付きリスト (コマンド / 操作者 / 戻し方) |
| 未決事項 | # / 決定タイミング / 項目 / 決定方法 の4列 |

### mermaidシーケンス図の micro 規約

- **alt 複数は点線が見づらい**、1 個に統合し失敗分岐は alt 内で完結させる
- actor 数は 3-4に限定する (User / API / DB / 別 service 程度)
- ラベルは短文化、図内に英文長文を入れない (詳細は本文に記載する)

## 想定SQLの書き方

コード全文は貼らない。意図のみbulletで。

| 項目 | 書く内容 |
|---|---|
| 対象 | テーブル・範囲 |
| 条件 | WHERE節の論理条件 |
| 並び順 | ORDER BYの意味 |
| 件数 | LIMIT |
| ロック | FOR UPDATE / SKIP LOCKED等の挙動 |

## 数値の書き方

- **OK**: ローカルベンチマーク、本番環境スペック (IaC参照)、本番データ集計 (公開API・メトリクス)
- **NG**: 仮定スループットから逆算した近似値、未検証の仮定値

仮定しか書けないものは未決事項として別に記載する。

## 専門用語の置換 (読者層に応じて)

| 専門用語 | 置換案 |
|---|---|
| Fisher-Yates | ランダムな順 |
| Parallel Change | 段階移行 |
| O(1) | 件数に依存しない |
| 冪等性ガード | 二重実行防止 |
| 同期ブロッキング | 完了まで応答を返さない |
| スループット | 書き込み速度 |

維持する: `p95` / SQL構文 (`SKIP LOCKED` / `FOR UPDATE` 等) / クラウド・OSS固有名詞。

### section 別に用語層を切替える

1つの DD 内でもsectionごとに読者層が異なる。サマリ系 sectionは PM / 他チーム engineer 想定で日本語優先、技術詳細 sectionは同領域 engineer 想定で英語慣用を許容する。

| section 性質 | 読者層 | 用語方針 |
|---|---|---|
| Overview / 監視 / 検証結果 / 結論 | PM / 他チーム engineer / SRE / QA | 日本語優先 (専門用語は初出で平易化) |
| 詳細設計 / 並行制御 / DB 内部 / SQL | 同領域 engineer / レビュアー | 英語慣用 OK (locking read / MVCC snapshot 等) |

**判断**: section 冒頭で「この sectionは誰が読むか」を 1 秒で判定して用語層を採用する。同section 内での揺れは禁止 (同じ単語が日本語と英語で混在する状態は最悪)。

### DB / 並行制御 領域の置換例 (架空)

| 専門用語 | 平易化置換 |
|---|---|
| MVCC snapshot | 単独の SELECT 文 |
| locking read | UPDATE 内 SELECT |
| 暗黙の Sロック | 自動取得される共有ロック |
| Xロック / Sロック | 排他ロック / 共有ロック |
| stale-write race | 古い値で書き戻す競合 |
| innodb_lock_wait_timeout | MySQLのロック取得待ち |
| Error 1213 | MySQLのデッドロックエラー (1213) |
| index range scan | 複合インデックスで範囲を限定して検索 |

**維持する**: SQL 識別子 (`FOR UPDATE SKIP LOCKED` / `READ COMMITTED`) / クラウドOSS 固有名詞 / 数式 (`O(1)`)。共有sectionでは平易化、技術詳細 sectionでは英語残置 (「section 別に用語層を切替える」参照)。

## 未決事項の書き方

「項目 + 決定方法」を対にして書く。決定方法がTBDなら表に含めず削除。

| 本文に記載する | 未決事項に記載する |
|---|---|
| 合意済みの方針 | 合意前の提案 |
| コード・計測で検証済みの事実 | 仮定・推定 |

## レビュー対応 (Step 4詳細)

- **3 分類対応**: 設計判断変更 = 本文書き直し / 説明不足 = 段落補足 / YAGNI 懸念 = 削除 or 未決事項へ

## PRD と PR コメントの優先順位 (SoT の扱い)

**Rule**: SoT (真の値) は PRD。だが PRD 本文が PR review や朝会で決まったことを反映しそびれるケースがある。整合性チェックで PRD と DD が食い違ったら、**PRD 本文だけでなく PRD 側の PR コメントも必ず読む**。PR コメントが真の確定事項のことがある。

**Why**: PRD 本文だけ見て整合性を判断すると方向を誤る。実際に「PRD が古く、PR review コメントで PdM が方針を変えた」ケースで Critical の方向を逆に出した事故がある。

**How to apply**:

- 整合性チェックで齟齬発見時: `gh pr view <N> --comments` で PRD PR のコメントを確認。inline も `gh api repos/.../pulls/<N>/comments` で読む
- PRD 修正は PdM 領域。DD に「PRD のここを修正する必要がある」節を作らない。齟齬は Slack / PR コメントで PdM に伝える
- 役割分担: PRD = 要件・背景 (PdM 管理) / DD = 実装方針 (エンジニア管理) / Figma = UI / PR コメント・朝会ログ = PRD 反映が遅れたときの真の決定源
- 実装詳細 (PRD に縛りがない範囲) は DD 側の設計判断で確定してよい

## Mermaid 構文の注意点

**書いたら検査する**: 図を含む file を保存したら `node ~/.claude/scripts/mermaid-lint.js <file>` を実行し、出力 0 件を確認してから doc を共有する。目視では気付かない誤りが多く、GitHub 上では描画が止まって初めて分かる。code fence (```` ```mermaid ````) と `<pre class="mermaid">`、`.mmd` file を対象にする。

頻出の誤り (linter が検出する分):

| 誤り | 直し方 |
|---|---|
| `A[失敗 (retry あり)]` — label 内の括弧 | `A["失敗 (retry あり)"]` と引用符で囲む。`(` `)` `[` `]` は quote しないと構文エラーになる ([公式 doc](https://mermaid.js.org/syntax/flowchart.html)) |
| `subgraph DB[(MySQL)]` | `[(...)]` cylinder は node 専用で、subgraph の title は `[...]` か引用符のみ |
| `A->B` / `A->>B` を flowchart で使う | flowchart は `-->` `-.->` `==>`。`->>` は sequenceDiagram の記法 |
| `subgraph` / `alt` / `loop` に対する `end` の数が合わない | 開いた block ごとに `end` を 1 行置く |
| `A --> B %% 注記` | `%%` の注記は行頭だけで、行の途中には書けない |
| `USER ||--o ORDER : places` | erDiagram の記号は左右の端と線種をそろえる (`||--o{` など) |
| 全角空白の混入 | 半角空白に直すか、label ごと引用符で囲む |
| node の id に小文字の `end` | 予約語なので `End` や `node_end` に変える |

- DB テーブル間の矢印は **FK 表現なら点線 `-. FK .->`**、実線は handler→table 等のアクセス関係。semantic 分離すると読み手が混乱しない
