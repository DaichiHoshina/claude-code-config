# コードコメント規約

コード内コメント (`//` `/*` `--` `<!-- -->` `#`) の書き方原則。
対象読者はコードレビュアー / 将来の自分 / AI エージェントとする。
対象外は PR 本文 / commit message で、それぞれ専用ガイドラインを参照する。

## 基本原則: default 書かない、書くなら Why not

記述対象の使い分け原則 (コード=How / テストコード=What / コミットログ=Why / コードコメント=Why not) は CLAUDE.md 「Writing」 が canonical。
記載するなら **Why not (なぜ別の選択肢を採らなかったか)** を記載する。例外は (a) 調べても見つけにくい外部 / 内部運用 memo (`MEMO:` prefix 必須) (b) 公開 API の godoc の 2 つだけ。
設計根拠 (WHY: なぜこの値 / 順番 / 挙動か) は commit log に記載するのでコードに書かない。コードに書かないと消える情報は「検討して却下した選択肢」にほぼ限られるからそうする。
コードを読めば分かる内容 (what) を繰り返すコメントは削除する。
迷ったら「その comment を消したとき、読み手の次の行動 (書き直しの誘惑 / API の誤用 / 運用判断) が変わるか」で判定する。変わらないなら削除する。

## 既存 comment を変更するかの判定 (最優先)

**本規約の分量上限・品質基準は「これから書く新規 comment」に対する目標であり、既存 comment を機械的に短縮する根拠にしない**。既存 comment を変更する前に、下記の順で判定する。

1. **理由と挙動を過不足なく説明できているか** → できているなら**そのまま維持する** (行数超過でも触らない)
2. 削除カテゴリ (what 言い換え / 開発経緯 / defensive 言い訳 / 主観評価 / commented-out code 等) に該当するか → 該当のみ削除
3. 内容は妥当だが冗長・曖昧・古い情報を含むか → その範囲だけ書き換える

**行数目安を理由に既存 comment を圧縮しない**。触った結果、読み手が失う情報 (理由 / 挙動 / 副作用) がある短縮は退行修正になる。分量が気になる時は「削るか、維持するか」の 2 択で判定する (中途半端に縮めない)。

文体規約の適用対象は `git diff <base>...HEAD` で `+` になっている行だけとする。base に元からある行は、実装と食い違っている場合を除いて触らない (レビュー済みの行への句読点・語順だけの書き換えは diff の雑音になる)。

## review で意味を問われた comment はまず書き換えを試す

「これはどういう意味でしょう?」と review で問われたら、まず書き換えを試す。意味を問われたのは書き方の問題であって、その comment が含んでいた情報 (Why not / 業務背景 / 非自明な副作用) が不要だったとは限らない。書き換えれば価値のある comment になる可能性を先に見る (user 指摘 2026-08-24)。

書き換えの向き:

- 状況を短い名詞句に縮めていれば、句を「何が / どんな状況で / 何が起きて / 誰がどう困る」の文に開く (「状況を自作の名詞句に縮めない」)
- 対処側のラベルだけで目的が書かれていなければ、「何をしない代わりに / 何が起きないように」採用したかを 1 句追加する
- 業務用語・設計用語を初出で使っていれば、括弧で意味を 1 句添える
- 「大づかみに圧縮」の運用でこの型を作った場合は、圧縮で落とすのが識別子と因果の段数だけで、状況の説明ではないことに戻る (「理由 + 対処」の guard)

削除を選択するのは、書き換えても価値が残存しないと言い切れる次の 3 case に限る:

- 元々 code の言い換え (what) や、隣接 code を読めば同じ結論に達する内容だった (「削除カテゴリ」 (1) / (11))
- 対になる関数や呼び出し先に同じ内容の comment が既にあり、片方が明確な重複だった (「削除カテゴリ」 (7))
- test がある理由を code 側に記載していた (test 側が含む情報)

書き直しで応じた comment が次の review でまた問われた場合も、削除でなく **書き方の型が違う** signal として扱う。名詞句を開く方向で書き換えたのに問われたなら対処側のラベルを書き換える、対処側を書き換えたのに問われたなら業務用語の意味不足を疑う、という順で書き手が使う語彙を reviewer 語彙に合わせていく。3 度問われた場合だけ、削除を選択する判定へ進む。

## 判定順序 (新規作成時)

**新規に comment を記載する**時のみ適用する。既存 comment の判定は上記「既存 comment を変更するかの判定」が優先する。

comment を記載する前に **(a) 記載するかどうか → (b) 何を記載するか (Why not に限定できているか) → (c) 日本語品質** の順で判定する。
日本語品質 rule (主語明示 / 開いた文章) を理由に comment を長くしない。品質 rule は「書くと決めた文」にだけ適用する。

- **default = 書かない**。迷ったら書かない (コードと識別子で伝わるなら comment は不要)
- **書くと決めた comment は日本語の文で書く**。既定言語と例外 (周囲が英語 / 公開 OSS / 読み手が日本語話者でない) の canonical は [PRINCIPLES.md 「出力言語の既定」](PRINCIPLES.md#出力言語の既定-日本語)
- **行数上限は設けない**。Why not + 根拠を過不足なく書けば足りるだけの行数を使う。1 行で足りるなら 1 行、複雑な incident workaround / 外部仕様 memo / 公開 API の godoc は必要なだけ書く
- 行数を埋めるために書き足さない。伝わる最短で止める
- comment 密度は周辺 code に合わせる。全行 / 全 block に付けない。迷ったら同じ dir の同種 file を `wc -l` と `grep -c` で数え、桁違いに多ければ書きすぎを疑う
- 後述「fail-safe / fallback 説明」は 1 文 default。目的文を追加するのは副作用が非自明な場合のみ

## 文末の句点「。」は付けない

comment の末尾に句点「。」を付けない (user 指摘 2026-08-03)。複数文を 1 comment に記載する場合、文の区切りの句点は残し、最後の文だけ句点なしで閉じる。この file の例文もこの表記で統一している。

```go
// NG: 呼び出し元の job scheduler が再実行を持つため retry は行わない。
// OK: 呼び出し元の job scheduler が再実行を持つため retry は行わない
```

## 配置: 該当行の真上に記載する

comment は説明対象の行の**真上**に置く。行末 comment や、対象から離れた位置 (数行上 / block 先頭にまとめる等) には書かない。読み手が comment と対象行を対応付ける手間をなくす目的。

- メソッド / 関数名の直上 comment は**そのメソッドの内容を簡潔に説明するもの**に限る (godoc 形式)。実装詳細や特定行の説明をメソッド直上に書かない
- **要約 1 行目が正しくても、2 行目以降にトレードオフや因果の説明を続けるのは同じ NG**。要約に詳細を後続させる形で混入しやすい。その説明が指す処理の真上へ移動するか、1 行に圧縮できないなら削除を検討する
- 特定行の WHY / 重要 memo は、その行の真上に記載する

### 置き場は「その comment が何を説明しているか」で決める

「真上」は対象が決まった後の rule で、指摘の大半は**対象の取り違え**で起きる (2026-08 の review 指摘 9 件を集計: 関数本体 1 行目に関数全体の説明 2 / 関数直上に特定行の説明 1 / 定義側に利用側の注意 1 / interface に実装の事情 2 / test に実装の理由 2 / 呼び出し側に helper の存在理由 1)。書く前に comment の主語を 1 つ言い、下表で置き場を決める。

| comment の主語 | 置き場 | 置いてはいけない場所 |
|---|---|---|
| 「この関数は」(関数の動作を述べる文。「〜を NULL にする」「〜を返す」のように関数名を言い換えて目的や契約を言う) | 関数の godoc | 関数本体の 1 行目 (本体が短くても、動作を述べる文は godoc へ) |
| 「この行 / この分岐は」(動作でなく理由や帰結だけを言う文 (「〜すると〜がズレる」)、または「〜なら」「〜のとき」の条件文で始まる文) | その行 / その分岐の真上 | 関数直上、block の先頭 |
| 「この helper が必要なのは」(helper の存在理由、呼ばないと何が壊れるか) | helper の godoc | 呼び出し側の行の真上 |
| 「呼んだ結果をこう扱うのは」(呼び出し先の挙動を受けた呼び出し側の対処理由) | 呼び出し側の対処行の真上 | helper の godoc (対処は呼び出し側の事情) |
| 「実装は」(接続先 / SQL 条件 / library 挙動) | 実装 struct / method 側 | interface の method godoc |
| 「使う側は」(戻り値の解釈や呼び出し側の行動。「〜とみなす」「〜せよ」「〜なら表示する」「〜として扱う」で終わる文) | 利用側の呼び出し行の真上 (複数箇所から呼ぶなら godoc に契約として 1 回) | 定義の直上 (定義が何をするか (「〜を返す」) を言っていない文は godoc ではない) |
| 「実装がこう振る舞う理由は」 | 実装 file | test file / test case 名 (test は What) |

文面の分類で迷う前に、位置から機械的に判別できる 2 つの合図を先に当てる (文面の判定より安定する):

- **関数直上の comment が関数名で始まらない** → 関数の説明ではない (godoc は関数名で始まる)。条件文なら分岐の真上へ、「〜とみなす」「〜せよ」なら使う側へ、理由だけなら該当行の真上へ移動する
- **godoc が無い関数の本体 1 行目に comment がある** → その comment は godoc 候補。関数名で始まる godoc に書き換えて関数直上へ置き、本体側は行固有の理由が残存するときだけ維持する

主語の見分けで迷いやすい 3 組:

- **「この関数は」と「この行は」**: 文が関数の動作を述べている (関数名の言い換えになっている) なら godoc へ移動し、本体側は消す (重複)。理由や帰結だけ、または条件文で始まる文は、その行 / 分岐の真上に置く。関数を実装しながら「まず何をするか」を記載すると本体 1 行目に落ちやすく、逆に分岐の条件を先に思いつくと関数直上に落ちやすい
- **複数文の comment**: 文ごとに主語を判定する。置き場が分かれる (契約 + 接続先 等) なら comment を分割して、それぞれの置き場へ移動する
- **「この関数は」と「使う側は」**: 「〜とみなす」「〜せよ」「〜なら表示する」のように、戻り値の意味づけや呼び出し側の行動を述べている文は「使う側は」。関数が何をするか (「〜を返す」「〜を数える」) を述べていない comment は定義の直上に置かない
- **「この helper が必要なのは」と「呼んだ結果をこう扱うのは」**: 呼び出し側に記載する理由が「helper の存在理由」なら helper の godoc へ (helper 名が理由を表していないことが多い)。「helper の挙動 (途中失敗でも先行分を返す等) を受けて、呼び出し側で何をしないと壊れるか」なら呼び出し側の対処行の真上で可

- godoc に記載すべき契約は返り値の形 (map の key が何か / nil を返さないか) と、名前から読めない振る舞い (論理削除済みを元に戻す等)。実装の内側を記載して契約が書かれていないと「この関数が返す値の説明が欲しい」と問われる
- godoc に「誰から呼ばれるか」「複数 usecase で共有する」は含めない (grep で分かる、削除カテゴリ (11))。それしか記載することがないなら契約が書かれていない signal で、返り値の形を記載する
- godoc の存在理由が特定の呼び出し元の事情 (「〜を保存する直前の検証で使うため」) になっているなら、置き場でなく設計を疑う。reviewer は「その処理は呼び出し元の method の中に持つべきでは」と読む (2026-08 実例)。呼び出し元に移動するか、呼び出し元に依存しない契約 (「最新値が必要な判定で使う」) に書き換える

```go

// rate limit が 10 req/s のため 100ms 遅延する

// 送信間隔を空けないと rate limit に当たるが、並列化すると順序保証が失われるため逐次送信を許容する
```

## 記載する 3 分類 (優先順)

### (1) Why not: 採らなかった選択肢とその理由 (原則これだけ書く)

「素直に書くならこうするはず」の選択肢を却下した箇所に記載する。次の読み手 (将来の自分 / AI) が「なぜこう書かないのか」と書き換えたくなる場所が対象で、退行修正を防ぐ効果が最も高い。
設計判断の根拠 (WHY: なぜこの値か / なぜこの順番か) はコードに書かず **commit log に記載する**。コードに記載する価値があるのは、書き直しの誘惑が生じる Why not に限られる。

```go
// retry は行わない。呼び出し元の job scheduler が再実行を持ち、二重 retry で送信が重複するため
send(msg)
```

```bash
# sed -i は BSD / GNU で引数仕様が異なるため使わない。一時 file + mv で置換する
sed "s/.../" "$f" > "$f.tmp" && mv "$f.tmp" "$f"
```

判定基準: そのコメントを消したとき、レビュアーが「普通は X では?」と指摘してきそうなら Why not を記載する。誰も別案を思いつかない箇所には含めない。

### (2) 重要 memo: 調べても見つけにくい外部 / 内部運用情報だけ (例外、`MEMO:` prefix 必須)

コード / repo 内 / 公式 doc をすぐ引けば分かる情報は書かない。記載するのは外部仕様の非自明な注意点・incident 由来 workaround・非公開制限・内部運用の取り決めのように「見ても調べても見つけにくい」ものだけ。
**`MEMO:` prefix を付ける** (Why not と区別し、機械的に grep 可能にする)。

```go
// MEMO: 外部決済 API の仕様で金額は円単位の整数。小数点以下は切り捨て (四捨五入では決済エラーになる)
amount := int(price)
```

### (3) godoc: 公開シンボルの API doc (行数制限なし)

公開 API の godoc / JSDoc / docstring は、次のいずれかを満たすときだけ記載する: 責務が名前だけでは分からない / 制約がある / 副作用がある / エラー条件が重要 / 利用方法に注意点がある / 名前だけでは誤解され得る。どれも満たさない自明な公開 API には含めない (「Create creates a shipment」は関数名の言い換えで価値ゼロ)。分担は godoc = What と契約、実装 comment = Why not で、How を godoc に含めない。private シンボルには原則付けず、記載するのは「実装を読むより godoc を読む方が理解が早い」場合だけとする。実装詳細や特定行の説明を含めない。swagger / OpenAPI annotation もこの分類に含む。

godoc は `go doc` / IDE hover / pkg.go.dev で参照される公開仕様 doc であり、code の実装 comment とは目的が別になる。使用例・引数説明・返り値・edge case・関連 API への言及など、利用者が API を正しく使うために必要な情報を記載する。冗長さは通常 comment と同じく避ける (書けば書くほど良いわけではない、書き手として不要な行は削る)。

関数 godoc は「何をするか」に加えて**「いつ呼ばれるか」(呼び出しタイミング)** を記載する。目的だけ記載した godoc は、読み手が呼び出し箇所を grep しないと使いどころを判断できない。記載するのは「どんな状況で使うか」であり、呼び出し元の関数名列挙ではない (関数名列挙は削除カテゴリ (11) に該当する)。

見た目と実際の契約が食い違う API には、その契約を 1 文で明記する。典型は path param `:id` を取る単一 resource 風の GET が、非存在 ID でも 404 でなく 200 + 空応答を返す場合で、明記しないと消費側が存在チェック用途に誤用する。

**執筆順序は「要約 → 利用法」で固定する**。1 行目でメソッドが何をするかを言い切り、続けて利用法 (呼び出し前提 / 呼び出し後に確認すべきこと / 典型的な呼び出しパターン) を記載する。順序を崩して利用法を先に記載すると、要約だけ拾い読みする読み手 (IDE hover は先頭行しか出さない) が契約を誤解する。

```go
// GetProductSizes は指定商品のサイズ一覧を返す。商品が存在しない場合も 404 でなく 200 + 空配列を返す
```

```go
// ProcessBatch は inventory_batch から未処理レコードを取得して集計する
//
// 集計単位は 1 バッチ = 最大 100 件。外部 API の rate limit (10 req/s) を
// 尊重し、100ms 間隔で送信する。ctx を cancel すると次バッチ開始前に停止し、
// 処理済み件数を返す。err は外部 API エラーおよび DB write エラー時に非 nil
//
// 呼び出し元は返り値の件数を必ず確認する (context cancel 時の部分成功を検知するため)
func ProcessBatch(ctx context.Context) (int, error) {
```

#### 書く価値があるのは「code を読む前に利用者が知るべき契約」

godoc は「code を読む前に利用者が読む doc」なので、code を読んでも分からない情報だけが価値を生む。書く対象は次に限る。

- API の契約: 入力の前提 / 返り値 / どんな条件でどのエラーを返すか (sentinel error 名まで書く)
- 副作用: 永続化 / 通知送信 / 外部呼び出しの有無
- 制約: 並行利用の可否 (safe for concurrent use か)、性能特性 (重い / 呼び出し回数の想定)
- 存在理由: その型・関数がなぜあるか (何の問題を防ぐか)。設計意図は code から読めない

型の godoc も同じ基準で、名前の言い換え (「Writer は data を書く」) でなく役割と制約 (「並行利用は不可」「〜の lifecycle を表す」) を記載する。関数名の言い換えだけの 1 行 godoc は削除カテゴリ (1) と同じ扱いで含めない。

const / var の godoc も意味 (何を制約・制御する値か) を記載する。「DefaultTimeout is default timeout」のような名前の言い換えは含めず、「外部 API 呼び出しの上限時間」のように利用側の判断材料になる情報を記載する。

```go
// NG: 関数名の言い換えで、利用者が新しく知れる情報がない
// Create は発送依頼を作成する
func (s *Service) Create(...)

// OK: エラー条件という契約を書く
// Create は発送依頼を作成する。同じ外部 ID の依頼が既にあれば ErrAlreadyExists を返す
func (s *Service) Create(...)
```

#### interface と実装の書き分け

interface の godoc には振る舞いと契約だけを記載する (何を返すか / 空入力の扱い / エラーにするか)。
実装への踏み込み (primary / replica どちらから読むか、SQL 条件、library 挙動、工夫の理由) は実装 code 側に記載する。実装を差し替えたら嘘になる文は interface に置かない。

```go
// NG: interface に実装詳細が漏れている (replica 読みをやめたら嘘になる)
// FindActive は replica から reserved_flag = 0 の row を SELECT して返す
FindActive(ctx context.Context) ([]Order, error)

// OK: interface は契約のみ。実装詳細は実装側の comment が持つ
// FindActive は有効な注文の一覧を返す。該当なしは空 slice を返し、エラーにしない
FindActive(ctx context.Context) ([]Order, error)
```

**判定基準**: その 1 文は「実装を丸ごと差し替えても真のままか」。偽になり得る文は実装側へ移動する。

この判定に合格しても、契約が足りているかを別に見る。「真だが不足」の godoc (引数による限定があるのに書かれておらず、全件返すように読める等) は真偽判定では捕まらない。利用者が入出力の範囲を誤解しないかで再確認する。

#### comment 密度の default は言語圏で異なる (FE は JSDoc 必須寄り)

「default 書かない」は Go 等の backend を想定した基準になる。frontend (TS / Vue / React) の project は、関数 signature・props・戻り値への JSDoc を規約で必須にしていることが多い。FE を実装するときは repo の lint / coding guidelines を先に確かめ、Go の基準を含めて省略しない。逆に規約とローカル慣習が衝突している場合は、一貫性を優先して見送る (例: test helper 群は JSDoc 省略が慣習)。修正するなら 1 file だけでなく suite 全体を別変更で合わせる。

#### package comment は契約として扱われる

package comment には package の責務と、隣接 package との責務分離を記載する。内部の実装構成 (「Writer struct を含む」等) は含めない。

package comment に記載した品質保証・互換性の宣言 (「旧経路と同一の出力を保つ」等) は、review で未検証の分岐や guard の非対称を指摘する契約基準として引用される。守り続けられない宣言を含めない。記載した宣言は test で裏付ける。

## 削除カテゴリ

### (1) what: コードの言い換え

コードを読めば分かる内容の繰り返しは削除する。

```go
// NG: i をインクリメントする
i++

// NG: エラーを返す
return err
```

### (2) PR 文脈依存: チケット番号単独 / 開発時の経緯

将来の読み手にはチケット番号だけでは内容が分からない。
チケット番号を記載するなら、なぜその対応をしたかを 1 文添える。

```go
// NG: #5678 対応
// OK: 外部サービスのタイムアウトが 30s に変更されたため、クライアント側も 30s に合わせる (issue #5678)
```

### (3) 自明アサーション: 型から明らかな制約

型システムや言語仕様で保証される内容を再説明しない。

```go
// NG: nil の場合は early return する
if err != nil {
    return err
}
```

### (4) defensive 言い訳: 「念のため」「とりあえず」「一応」

不確かさを表明するコメントは実装の問題を隠す。正しく実装してからコメントを記載する。

```go
// NG: 念のため nil チェック
// NG: とりあえず 0 を返しておく
// NG: 一応ログを出しておく
```

### (5) 主観評価: 根拠のない「十分」「余裕」「問題ない」

客観的な根拠のない評価は将来の意思決定を誤らせる。
数値や条件に置換するか削除する。

```go
// NG: タイムアウトは十分な余裕がある
timeout := 30 * time.Second

// OK: 外部 API の p99 応答が 8s のため、2 倍余裕を持って 16s に設定する
timeout := 16 * time.Second
```

### (6) テスト不確実表現: 「〜するはず」「おそらく」

テストや検証で確認してから断言する。

```go
// NG: これで重複が防げるはず
// NG: おそらくここでキャッシュが有効になる
// OK: Redis の SETNX で排他制御する。同一キーへの並行書き込みは先着 1 件のみ成功する
```

### (7) 重複: 同一概念を複数箇所で説明

同じ内容のコメントが複数箇所にある場合、最も文脈に近い 1 箇所だけ記載する。

### (8) 経過メモ: 開発中の変遷・時系列記述

コメントは**現在のコードの事実のみ**を記述する。開発中の変遷 (「〜から変更」「以前は〜だった」「レビュー指摘で修正」「当初 X だったが Y にした」) は git history / PR が保持するため、コードに記載しない。

```go
// NG: 当初は 30s だったが timeout 頻発のため 60s に変更
// NG: レビュー指摘により defer に書き換え
// NG: v2 移行に伴い旧ロジックから差し替え
// OK: 外部 API の p99 応答が 45s のため 60s に設定する
timeout := 60 * time.Second
```

経緯に WHY が含まれる場合は、経緯部分を削って現在形の根拠だけ記載する。

### (9) commented-out code: 削除予定コードを記載しない

不要になったコードは削除する。version control が履歴を保持するため、コメントアウトする必要はない。

```go
// NG: 旧実装を残す
// result := oldCalculate(input)
result := newCalculate(input)
```

例外: 短期 (≤1 sprint) の A/B 切替や、PR レビュー中の比較目的で一時的に維持する場合のみ。その場合は **`TODO:` prefix + 理由** を 1 行添える (`TODO:` で機械的に grep 可能にし、削除し忘れたときの回収経路を確保する)。

```go
// TODO: 旧計算式。A/B 比較が終わったら削除する
// result := oldCalculate(input)
result := newCalculate(input)
```

### (10) 他の宣言を参照させるだけ

「理由は X と同じ」のように、参照先を読まないと意味が分からない comment は削除する。comment 単体で意味が完結しないものは情報を含まない。理由の本文は最も文脈に近い 1 箇所だけに記載する ((7) 重複と同じ帰結になる)。

```go
// NG: 理由は Create と同じ
```

### (11) grep / IDE で分かる情報

呼び出し元や利用箇所の列挙を含めない。grep / IDE の参照検索で分かる上に、呼び出し元の追加・削除で嘘になる。同様に、同じ file の数行 (template / 呼び出し元 / 1 行だけの実装) を読めば同じ結論に達する理由説明も、Why not の体裁でも削除する。godoc に記載する「いつ呼ばれるか」は呼び出し状況の説明であり、この列挙とは別 ((3) godoc の節)。

```go
// NG: RequestShipment から呼ばれる
```

## TODO は解消条件付きで書く

一時対応の code に付ける `TODO` は **`TODO: <解消条件>` の形式**で書く。単発の `TODO` や「一旦入れています」だけの memo は、何を待てば消せるか分からず回収されない。

- 何を待って解消するかを記載する (issue 番号 / 後段 PR / 移行完了 等)。参照先があれば link を付ける
- 削除予定なら「削除する」と明記する

```go
// NG: TODO
// NG: 一旦入れています
// OK: TODO: 論理削除への移行が終わったら削除する (issue #1234)
```

## 意図的な冗長 (defensive redundancy) は 1 行 comment で明示する

「(4) defensive 言い訳」で削除するのは「念のため」等の**不確かさ表明**である。区別して、**故意に条件を二重に記載した保険的な冗長**は維持する。ただし意図が読み取れない冗長は refactor で消されるため、**1 行 comment で「何を守るか」を必ず添える**。

典型例は SELECT で限定した id を UPDATE / DELETE に渡す構造で、UPDATE / DELETE 側にも同じ where 条件を重ねて書くパターン。SELECT filter が守っている前提では UPDATE 側の条件は理論上 noop に見えるが、SELECT filter が将来 refactor で壊れた場合の最後の砦として機能する。

```sql
-- NG: 意図が読み取れず「重複だから消そう」となりやすい
SELECT id FROM orders WHERE reserved_flag = 0 AND processed_at IS NULL FOR UPDATE;
UPDATE orders SET processed_at = NOW() WHERE id IN (...) AND reserved_flag = 0;

-- OK: comment で保険の意図を明示する (構造は NG と同じ)
SELECT id FROM orders WHERE reserved_flag = 0 AND processed_at IS NULL FOR UPDATE;
-- SELECT filter が破れても予約済み row (reserved_flag = 1) を書き換えないよう UPDATE 側でも守る保険
UPDATE orders SET processed_at = NOW() WHERE id IN (...) AND reserved_flag = 0;
```

**判定基準**:

- SELECT で限定した id を UPDATE / DELETE に渡す構造で、UPDATE / DELETE 側にも同じ where があったら意図を確認する
- 意図的な保険なら 1 行 comment で「どのカラムが守られるか」を記載するよう指摘する
- 逆に「重複だから消したい」を見つけたら、SELECT 側の filter が絶対に外れない保証があるか確認してから消す

同じ判定は API 層の権限チェック二重化 (route middleware + handler assertion)、frontend の入力バリデーション二重化 (client-side + server-side) にも当てはまる。**二層目が理論上 noop に見える場合、意図 comment がないと片方が消される。**

## 規約から意図的に外れるときは理由をその場に記載する

lint / coding 規約 / repo の定型 pattern から意図的に外れる行には、「なぜ例外か」(必要ならテストでの扱いも) を comment で添える。理由がその場にないと、review (人間 / bot) が毎回同じ指摘を再発火し、次の書き手が規約準拠へ「修正」して退行させる。理由 comment は Why not (規約通りにしなかった理由) の一形態で、review 指摘への防御としても機能する。

```go
// NG: 規約 (mock 可能な request 時刻を使う) 違反に見え、毎回指摘される
deadline := time.Now().Add(readTimeout)

// OK: 例外の理由を添える
// socket の read deadline は OS が実時刻で評価するため、mock された過去時刻を
// 基準にすると即 timeout する。ここは規約の例外として time.Now() を使う
deadline := time.Now().Add(readTimeout)
```

## AI 時代のコメント

### AI 生成マーカー禁止

`// AI-generated` / `// TODO: AI suggested` / `// Generated by Copilot` 等の生成元マーカーは含めない。レビュー時に判断根拠が「AI が書いた」に矮小化され、人間レビュアーが思考停止する原因になる。詳細: `references/on-demand-rules/ai-output.md`。

### Comment Traps 回避

削除予定コード / 古い WHY コメント / 「(8) commented-out code」の例外なき長期放置は、AI コード生成 (Copilot / Claude Code 等) が **「有効な現役例」と誤読** して誤った提案の原因になる。コメントと実装の乖離を放置せず、コード変更時に同 PR で更新または削除する。

出典: arxiv 2024 "Comment Traps: How Defective Commented-out Code Augment Defects in AI-Assisted Code Generation"。

## 日本語品質

コメントの本文は既定で日本語で書く (「判定順序 (新規作成時)」)。以下はその品質基準とする。
**guard: 以下の品質 rule は「書くと決めた行」にだけ適用する。** この節の OK 例は NG 例より長いが、これは「書くと決めた文の書き換え方」であって「長く書くほど良い」ではない。書き換えると長くなる comment は、その前にまず削除 (what 言い換えなら書き換えではなく削除が正解) を検討する。

### 主語明示

主語を省略すると「誰が / 何が」動くかが曖昧になる。

```
NG: 取得に失敗した場合はスキップする。
OK: 設定値の取得に失敗した場合は、該当レコードをスキップして次の処理に進む。
```

### データ保持識別子の godoc は名詞述語で閉じる (動作動詞禁止)

const / var / struct field などデータを保持するだけの識別子の要約に、動作動詞 (「まとめる」「持つ」「管理する」「制御する」) を付けない。入れ物は動作しない。「何であるか」を名詞 (一覧 / 組 / 対応表 / 既定値) で言い切る。

```
NG: // ExcludeKeys は、重複チェックの対象から外すプロダクトとサイズの ID をまとめる。
OK: // ExcludeKeys は重複チェックの対象外にする (プロダクト ID, サイズ ID) の組の一覧。
```

NG 例は「Keys がまとめる」という主述不一致に加えて、次項の修飾連鎖も同時に踏んでいる。

### 連体修飾の連鎖回避 (かかり先曖昧)

「A の B の対象から`外す` C と D の ID」のように修飾が 3 つ以上連なると、`外す`「の」のかかり先が複数解釈になる。読み手が「C の ID と D の ID なのか、(C, D) の組なのか」を問い返したくなったら書き換える。組・一覧・対応表などの構造語と括弧表記 `(X, Y) の組` で構造を固定する。

### 長い識別子名の godoc は名前の反復を省ける (「英語だらけ」の切り分け)

comment が「英語だらけで読みづらい」と感じたら、地の文の英語一般名詞 (後述 「地の文の英語名詞」) と識別子名の反復を分けて数える。反復が主因なら語彙をカナへ開いても解決しない。長い識別子 (40 文字前後の const 名等) に「識別子名 は〜」形式の godoc を並べると、1 行の大半が識別子で埋まり、日本語の説明が右端に押し出されて読めなくなる。

- const 群の godoc は識別子名を省いて説明だけ書いてよい。同 repo に前例があるか grep で確認してから省く (前例があれば convention 違反にならない)
- struct / interface method の godoc は識別子名で始める慣習を維持する (IDE hover が先頭行しか出さないため、名前がないと何の説明か分からなくなる)
- 判定基準: その行を読んだとき、日本語の説明部分が識別子名より短いなら書き方を変える

### 「ため」連鎖回避

「〜のため〜のため〜のため」と続くと因果関係が不明確になる。2 文に分割する。

```
NG: 外部 API のレート制限があるため処理件数を制限するためスリープを入れる。
OK: 外部 API のレート制限は 10 req/s。超過時は HTTP 429 が返るため、100ms のスリープを入れて送信する。
```

### 半角スペース: 英数字と日本語の間

```
NG: Versionチェック、IDを取得する
OK: Version チェック、ID を取得する
```

### 二重否定回避

```
NG: null でない場合は処理しない
OK: null の場合のみスキップする
```

### 接続詞乱用回避

「しかし」「また」「さらに」「なお」が連続すると流れが追いにくくなる。
文を分割するか接続詞を削除する。

## 「変に略さない」原則

体言止め圧縮で主語が物や状態に移り、擬人化が生じるパターンを避ける。

この節は code comment への当て方を扱う。擬人化を避ける原則そのものは chat 応答にも適用し、canonical は [PRINCIPLES.md 「自然な話し言葉の日本語」](PRINCIPLES.md#自然な話し言葉の日本語-英語の混在抑制) にある。

### 擬人化 NG パターン

| NG | OK |
|---|---|
| `--dry-run flag 未渡しが実際の INSERT を走らせないようにする` | `--dry-run flag が指定されなかった場合に、意図せず実際の INSERT が実行されることを防ぐ目的` |
| `flag 未指定時は dry-run=true` | `dry-run flag の取得に失敗した場合は安全側として dry-run=true として続行する` |
| `タイムアウト到達で処理中断` | `タイムアウトに達した場合は、処理中のバッチを中断して部分的な結果を返す` |

**違反典型**:
- 主語が物 / 状態 / flag の擬人化 (「flag が〜する」「エラーが〜する」)
- 口語動詞 (「倒す」「握る」「進まれる」)
- 連用形否定 (「未渡し」「未指定時」) — 「指定がない場合は」と展開する

### 多義語は文脈で明示化

「打ち切り」「同期」「中断」「停止」のように **文脈依存で意味が変わる単語** は、何の打ち切りか / 何との同期かを 1 語添えて明示化する。

| Before (多義) | After (文脈明示) |
|---|---|
| `打ち切り` | `別 TX 更新の中断` |
| `同期更新` | `別 TX で実行する更新` (「同期」が時系列同期と読まれる懸念) |
| `中断` | `retry を諦めて log 出力する` |
| `停止` | `worker process の終了 (再起動可)` |

**判断基準**: 単語単独で読み手が「何の」と問い返したくなったら多義。1 語で意味を固定する。

### 略称・外部 doc 前提の代名詞禁止

**code comment 内で「3 識別子」「A 系」「例の flag」等の略称や、DesignDoc / 社内 slack を前提とした代名詞を使わない**。code reader は当該 DesignDoc を読んでいる保証がない。初出は 1 句で具体名に展開する。

| NG | OK |
|---|---|
| `3 識別子は size_codes 側だけが持つため、products 側を NULL にする` | `has_size = true のとき inhouse_code / item_variant_id / item_variant_code は size_codes だけが持つため、products の同フィールドには NULL を設定する` |
| `例の flag が立っていれば skip する` | `enable_new_pipeline flag が true なら旧経路を skip する` |
| `A 系と B 系の判定は DesignDoc 参照` | `admin API 経由 (A 系) は同期処理、batch 経由 (B 系) は非同期。詳細: <URL>` |

**判断基準**: comment 内の名詞句が「同 repo の別 file を grep すれば意味が特定できる」か。特定できない (外部 doc を要する) 名詞は展開するか URL を添える。

### client 側の主語は役割名で書く (実装 stack 名の禁止)

comment / godoc / commit log で client 側 (Web / iOS / Android の総称) の挙動を語るときは、主語を「UI」等の**役割名**で書く。実装 stack 名 (Vue / React / Flutter) を主語にすると、読み手に stack 知識を要求し、実装を移行したら嘘になる。契約 (何が飛んでくるか) を語るとき、client 実装の内部詳細は関係ない。

```go
// NG: Vue は has_size = true のとき ItemCode に null を送る
// OK: UI は has_size = true のとき ItemCode に null を送る
```

stack 内部の詳細そのものを語るとき (「Vue の型生成が全 field optional で〜」等) だけ stack 名を使う。

### 曖昧語・因果逆転の禁止

読み手が手順や因果を推測しないと意味が確定しない語 (「先に」「後で」「退避」「〜するため」の因果逆転) を使わない。動作の実体と因果の向きをそのまま書く。

| NG | 問題 | OK |
|---|---|---|
| `先に無効化する` | 何より先か読み取れない | `重複を作らないよう、旧 row を無効化してから新 row を挿入する` |
| `旧値を退避する` | 元へ戻す前提に読める (実体は上書き) | `旧 row を無効値で上書きする` |
| `rollback するため重複を消す` | 因果が逆 (rollback は結果) | `一意制約違反で TX が rollback されるので、事前に重複を消す` |

### godoc / 関数コメントと実装内 comment は重複させない

関数直上の godoc で説明した内容を、関数内 comment で繰り返さない。実装内 comment は Why not / 分岐理由に限る (canonical 「記載する 3 分類」)。重複した実装内 comment はレビューで削除を促される。

### 独立 directive は隣接シンボルと空行で分離する

`//go:generate` / `//go:build` / `// +build` / linter 抑制 (`//nolint:xxx`) 等の**独立 directive は、直下の関数 / 型定義と意味的に無関係な場合、無関係シンボルの直上に置かない**。位置による関連付けを避けるため 1 行空行を入れる。

例:

```go
// NG: OrderProduct と無関係な directive が隣接し、関連ありに見える
//go:generate mockgen -source=product.go
type OrderProduct interface { ... }

// OK: 空行分離で無関係を示す
//go:generate mockgen -source=product.go

type OrderProduct interface { ... }
```

**判断基準**: directive の対象が directive 直下のシンボルでない場合は空行を入れる。対象が直下シンボル (例: `//nolint:xxx` が直下 func に適用される) なら密着で可。

## 識別子は用語変更しない (ログ互換性のため)

DD / コメント / docs 本文で用語をリネーム (例: 「同期更新」→「別 TX 更新」) する時、コード上の **識別子 (const 名 / 変数名 / feature flag tag / log key / metric 名)** は据え置く。

**理由**: 識別子変更は log 検索 / metric query / feature flag 履歴を破壊する。コメント / docs は文脈で正しい用語に従う一方、識別子は **時系列で安定** していることが運用上必須。

**判断**:
- 更新する: コメント本文 / docs 本文 / PR タイトル / commit message
- 据え置く: const 名 / 変数名 / struct field 名 / feature flag tag / log key / metric 名 / DB column 名

例 (架空):
- 用語 rename: `同期更新` → `別 TX 更新` (コメント / docs)
- 識別子: `productSyncTimeout` / `product_sync_failure` (feature tag) はそのまま (log 検索互換性のため)

リネームと同時に識別子も変えたい場合は、log query / metric / runbook の更新コストを見積もり、別 PR で行う。

## 「理由 + 対処」を 1 文で閉じる

Why not を記載するなら、対応する動作 (「なので〜する」「そのため〜する」) を同じ 1 文に含める。理由だけ記載して対処を含めないと、読み手は理由から動作を逆算する手間を負う。動作だけ記載すると what の言い換えになりがちで削除対象になる。

- 定型: `〜すると〜になるので、〜する` / `〜だと〜が起きるため、〜する`
- 理由と対処の関係が一度で読めるなら同じ文に置く。字数を収めるためには分割しない
- Why not の文に HTTP status code・識別子名・複数の因果の連鎖が並んだら、「何を守るか」の核心だけ記載して大づかみな 1 文に圧縮する。再現困難な bug の再発防止など具体が必要な場合だけ連鎖を含める。圧縮で落とすのは識別子と因果の段数であって、状況の説明ではない。状況を短い名詞句に言い換えて縮めるのは別の失敗になる (次節)
- 説明が長くなるなら、そもそも comment が必要か、設計資料へ置くべきかを再検討する

```go
// NG (what 言い換え): 削除した行も無条件に別 table へ移動する
// NG (理由だけ): 削除した行の sort_order を残すと次回の保存で重複エラーになる
// OK (理由 + 対処): 削除した行の sort_order を残すと次回の保存で重複エラーになるので、削除対象もまとめて別 table へ移動する
```

## 状況を自作の名詞句に縮めない (「どういう意味?」の主因)

書き手の頭の中にある状況を「有効行 0 件化」「誤同梱」「両方の値」「片側に伝播しない」「共有点」のような短い名詞句へ縮めて書かない。読み手はその句が指す状況を知らないので、単語を並べられても意味を復元できず、「これはどういう意味でしょう?」と問い返すしかなくなる。2026-06〜08 の自分の PR で review が comment の意味を問い返した 21 件 (8 PR) を集めた。DesignDoc 略語 (「略称禁止」) や多義語 (「多義語」) より、この型が大半だった (user 指摘 2026-08-24)。

名詞句を「何が / どんな状況で / 何が起きて / 誰がどう困る」の文に開く。名詞句の意味と目的を、その領域を知らない人が読んでも分かる日本語で書く。

| NG (状況を名詞句に縮めた) | OK (状況と目的を文に開いた) |
|---|---|
| `有効行が残り 1 件の場合のみ非活性にして 0 件化を防ぐ` | `全行を無効にするとこの商品ではサイズを 1 つも選べなくなるため、有効なサイズ行が最後の 1 件のときは無効化の操作を受け付けない` |
| `誤同梱を防ぐためサイズ関連 field のみ空値に倒す` | `サイズ情報に矛盾がある景品の値をそのまま画面に出すと発送担当者が別サイズの商品を箱に入れてしまうため、サイズ名と識別子を空で返す` |
| `不整合行では両方の値が無く NULL になる` | `商品側にもサイズ側にも識別子が入っていない行は列が NULL になるので、string でなく NullString で受ける` |
| `分岐ごとに初期化を複製すると field 追加が片側に伝播しない` | `通常の行と矛盾のある行で struct の初期化を別々に書くと後から field を追加したときに片方だけ書き忘れるため、1 か所で初期化してから上書きする` |
| `存在しない order_id が含まれると件数が減るため 400 で拒否する` | `依頼に含まれる注文 ID の一部が存在しないと取得件数が依頼件数より少なくなるので、存在しない注文を含む依頼を受け付けないよう件数が一致しなければ 400 を返す` |

(例は実 PR の comment を基に書き換えたもので、OK 側の業務上の理由は例示に合わせて補っている。文に開いても理由と対処は 1 文で閉じる (前節))

**書いた直後の self-check**:

- 判定の単位は名詞句でなく comment 全体にする。comment を最後まで読んで、その句が指す状況 (何が / どんなとき / 何が起きる) を読み手が文中の他の語から復元できるなら、句が短くても指摘しない。復元できず、句を開かないと文全体の意味が確定しない場合だけ造語として扱い、文に開く。名詞句を 1 つずつ単体で採点すると、問題のない comment の半数を要書き直しにしてしまう (2026-08-24 の実測: 質問されなかった comment 8 件のうち 4 件を誤検知)
- 復元できるかの目安は「何が (主語) / 何を (対象) / どうする (動作)」の 3 つを句の外から補わずに言えるか。repo grep は識別子や定数名の実在確認には使えるが、日本語の句は大抵 0 hit になるので判定には使わない
- 名詞句に「化」「側」「局所」「残留」「両方」「片側」等の圧縮語が入っていたら、何が何をどうする話かを主語と動作で補って再確認する
- 「〜のため」の前に置いた語 (誤同梱 / 件数が減る) が、仕組みの説明で止まっていないか見る。読み手にとっての困りごと (誰が何をしてしまうか) まで書く
- 対処側の句にも同じ目で見る。「adapter 局所で定義する」「構造だけを固定する」「純関数として固定し test で守る」「最低サポート対象」のように、採った対処や状態を書き手のラベルで呼んでいる句は、文として読めても読み手には「局所とは? 固定とは?」の問いが残存する。そのラベルが「何をしない代わりに / 何が起きないように」採用したものかが comment 内に書かれていなければ、目的を 1 句追加して開く (2026-08-24 の実測: 文として読める comment でも、この型の 5 件は全部 review で意味を問われた)
- 業務用語 (没収 等) や設計用語 (grandfather 等) を初出で使うなら、括弧で意味を 1 句添える。定数名の併記は意味の説明にならない
- 書き換えた文が長くなるのは正常。長さを理由に名詞句へ戻さない。長さが気になっても、まず書き換えの向き (「review」 で意味を問われた comment) を試してから、削除の 3 case に当てはまるかを見る

## 「状況 → 読み手の結果 → コードの対処」の順で、対処は識別子で書く (user 確定 2026-08-28)

前節で文に開いた comment の語順と語の選び方を固定する。PR body / commit / review 返信 / issue へ同じ型を当てる媒体別の表は `PRINCIPLES.md` 「状況 → 読み手の結果 → 対処」が canonical で、この節は code comment への当て方だけを扱う。雛形は `hidden のときは画面がサイズ欄を出さないので、Label は空のまま返す` で、分かりにくい comment の主因は、主語が `UI` / `status` / `文言` のように抽象で、何が起きて何を空にするかが復元できないことだった。

### 1 文の型

1. **状況**は、コードを見なくても分かる具体名で書く: `hidden のとき` / `発送依頼済みなのにサイズを特定できないとき` / `選べるサイズが無いとき` / `map の反復順に依存すると`
2. **結果**は、画面や呼び出し側がどう見るかを記載する: `画面がサイズ欄を出さない` / `成功の空一覧として出す`
3. **対処**は、この行が触る識別子と値で書く: `Label は空のまま返す` / `HasMissingData を true にして返す` / `監視ログだけ記録する`

「なので」の前が状況と結果、後ろがこの行の動作 (「「理由 + 対処」を 1 文で閉じる」)。理由だけ、動作だけにしない。読み手が見る側は `FE` でなく役割名 (画面 / 発送担当者 / 呼び出し元) で書く (「client 側の主語は役割名で書く」)。

1 文に入れてよいのは理由と対処の 2 つまでとする。対比や帰結が 3 つ目として入るなら、意味の切れ目で 2 文に切り、帰結は「そのため」で始める。

### 使わない語

| 分かりにくかった語 | 直し方 |
|---|---|
| `UI` / `FE` / `BE` / `status` / `文言` | `画面` / `hidden` / `Label` のように、読み手が見るものと code の識別子で書く |
| `立てて` | `true にして返す` (bool をどの値にするかを記載する) |
| `流す` `倒す` `詰める` `引く` `出す` | 監視ログへ記録する / 表示しない / 空のまま返す / 取得する、と意味をそのまま動詞で書く |
| `登録漏れ` `このケース` `欠落` `専用の分岐` `決定的` | 状況を文に開く (「状況を自作の名詞句に縮めない」) |
| `4xx` / `200 + sizes=[]` | `画面が成功の空一覧として出す` のように、結果側を読み手の見え方で書く |
| `もの` `側` `面` | 対象を名指しする (`保有中の注文` / `無効な行` / `Keeping`)。「もの」は user が禁止 (2026-09-15) |
| `〜だけ` `別の〜` `暗黙に` | 比較対象と主語と時点を同じ文に記載する。「1 つだけで足りる」は何と比べて 1 つか、「暗黙に無効化される」は誰が無効化するかを添える |
| `断る` `断つ` | `400 でエラーにする` のように、返す status と動作で書く |
| `無効になる` (結果だけ) | `request から削除された` のように、読み手が探す操作の名前で書く |
| `入力` | API の話なら `request` と書く。画面の入力欄と読み違えられる |

### 重複の判定

- 同じ「一覧は返す・エラーにしない・ログだけ記録する」を godoc と本体の両方に書かない。理由は `logger.Error` を呼ぶ行の真上に 1 回だけ置く (「godoc / 関数コメントと実装内 comment は重複させない」)
- 結果の言い回し「画面がサイズ欄を出さない」が、ゼロ値の `Hidden`、`HasMissingData`、view の `Label` のように対処が違う行に付くのは重複ではない。対処が違えば別の comment として記載する
- view の godoc で `サーバー側` と `BE 側` を並べない。語を合わせないと「画面側が組み立てない」という契約が消える

### 修正して分かったこと (2026-08-28 の実例)

- `画面に登録漏れ専用の分岐を持たせないので、4xx ではなく 200…` は、状況 (登録漏れ) も結果 (4xx / 200) も書き手のラベルのまま。`発送依頼済みなのにサイズを特定できないときは、画面が成功の空一覧として出すので、HasMissingData を true にして返す` に開く
- `HasMissingData を立てて` は、bool を true にする動作が見えない
- FetchMap の godoc と本体に同じ「ログだけ記録する」を記載すると二重になる。本体の `logger.Error` 直上 1 回にまとめる

この型は新しい規範ではなく、この file の既存節を雛形 1 文から逆算して束ねたものになる。書き換えのときに guideline を再度開けなくても、雛形 1 文を分解すれば同じ判断に戻れる。出所の対応:

| 判断 | 出所の節 |
|---|---|
| 「なので」の前が状況、後ろが対処 | 「「理由 + 対処」を 1 文で閉じる」 |
| `欠落` `このケース` `決定的` を開く | 「状況を自作の名詞句に縮めない」 |
| `流す` `倒す` `詰める` をやめる | 「「変に略さない」原則」 / 「擬人化 NG パターン」 |
| `UI` / `文言` でなく `画面` / `Label` | 「主語明示」 |
| `FE` を画面側に開く | 「client 側の主語は役割名で書く」 |
| 指摘のない行と fixture の句点は触らない | 「既存 comment を変更するかの判定」 |
| godoc の要約行は型に合わせない | (3) godoc の節 |

適用範囲は新規に記載する comment と、review で意味を問われた comment の書き直しに限る。指摘されていない既存 comment や、句点を削っただけの fixture comment はこの型に合わせる目的で触らない。godoc の要約行は型や関数そのものの説明なので、「〜のときは」型に無理に合わせない。

```go
// NG (抽象主語 + 口語圧縮): 非表示 status では文言を設定せず空に倒す
// OK (状況 → 結果 → 対処): hidden のときは画面がサイズ欄を出さないので、Label は空のまま返す
```

## 理由は積極形で書く (消極形の禁止)

理由付けを消極形 (「〜を避けるため」「〜しないため」) で書かず、積極形 (「〜を検証するため」「〜の契約を満たすため」) で書く。消極形は実在しない rule / イディオムが実在するかのような印象を作り、書き手自身が後で事実確認せず引用する誤情報の発生源になる。積極形で書けないなら、その実装を採用した判断自体がまだ言語化できていない signal として扱い、書式の選定に戻る。

「〇〇と同じ方式」と参照を示すときは、参照先の layer / 対象 / 目的が一致していることを実物で確認してから書く。層違いの前例を示すと、レビュアーに参照先ごと疑われる。

```go
// NG: レプリカ遅延を避ける (xxx_test.go と同じ方式)
// OK: 書き込み直後の読み出しを primary に向け、seed した row が読めることを検証する
```

## test comment は現在の故障 mode を記載する

test の意図 comment に将来仮定 (「〜された時の回帰保険」「〜に備えて」) を含めない。実在しない将来の故障 mode への言及は「今は不要」と読まれ、test 自体の必要性まで疑わせる。今ある制約と、この test が何の故障をどう検知するかをそのまま記載する。将来 refactor への先回り説明は code でなく PR body / review 返信に置く。

```go
// NG: UPDATE 文が書き換えられた時に SET 漏れを検知する回帰保険
// OK: 手書き SET 句は列挙した column しか更新しないため、全 column の値を突き合わせて更新されない column を検知する
```

## 英単語 +「化」の圧縮禁止

共通 canonical は [NG-DICTIONARY.md](NG-DICTIONARY.md) の「英単語 + `化` の圧縮」行で、この節は comment での判定例だけを扱う。

「true 化」「slot 化」「無効化」など、英単語 (または短い語) に「化」を付けて動作を圧縮する書き方は、主語が消えて何が起きるか読み取れない。主語のある文に開く。

```
NG: OR 条件で誤って true 化しない
OK: OR でつなぐ実装が、どれも一致しないのに true を返さない
```

「化」を用いてよいのは業務用語 (可視化 / 標準化 / 非同期化 等) として定着している場合のみ。「〜化する」で主語が物や状態になったら擬人化 NG (「変に略さない」原則 「擬人化 NG パターン」と同じ判定)。

## fail-safe / fallback 説明は 1 文 default

安全側への倒しや代替動作の説明は 1 文で書く。

```
// {対象} の {取得失敗 / 不在 / 解析エラー} の場合は安全側として {既定値} として続行する
```

```go
// inventory_batch の設定ファイル解析に失敗した場合は安全側として dry-run=true として続行する
dryRun := cfg.GetBoolSafe("dry_run", true)
```

2 文目 (「{誤操作シナリオ} で {副作用} が発生することを防ぐ目的。」) を追加するのは、**防ぎたい副作用がコードから読み取れない場合のみ**。dry-run のように既定値の意図が自明なら 1 文で止める。テンプレを全 comment の雛形にしない。

## 英単語 +「する」動詞化回避

共通 canonical は [NG-DICTIONARY.md](NG-DICTIONARY.md) の「英単語 + `する` の動詞化」行で、この節は comment での判定例だけを扱う。

地の文の動詞は日本語で書く。識別子・コマンド名はバッククォートで囲い動詞化しない。

| Before | After | 備考 |
|---|---|---|
| `1 件でも失敗があれば非 0 exit する` | `1 件でも失敗があれば終了する` | exit code の詳細は数値に意味がある場合のみ記載する |
| `不一致を検出 (非 0 exit)` | `不一致を検出した場合は終了する` | 括弧書き → 文に展開 |
| `ctx を cancel する` | `ctx をキャンセルする` | 英語動詞 → カナ動詞化 |
| `lock を acquire する` | `ロックを取得する` | 英語名詞・動詞 → 日本語 |

**判断基準**:
- 識別子 (`ctx` / `dryRun` / `--dry-run`) はバッククォートで囲い、動詞は日本語で添える
- `exit code 1 で終了する` など数値に意味がある場合は英単語を維持してよい
- 地の文の動詞を英語のままにしない

## 地の文の英語名詞はカナ / 日本語へ開く (user 指摘 2026-08-19)

本規範は code comment に限らず、review comment / PR body / issue / commit message 等の外向き文章全般に適用する (共通 canonical: [PRINCIPLES.md 「自然な話し言葉の日本語」](PRINCIPLES.md#自然な話し言葉の日本語-英語の混在抑制)。この節は具体例一覧を扱う)。

動詞だけでなく、地の文の**一般名詞も英語のまま置かない** (「error 判別」「rollback は〜」等)。英語のまま維持する語は (a) code 識別子・関数名・型名 (b) 固有名詞 (製品名 / API 名) (c) 和訳すると通じにくい開発用語 (SQL / API / TX / mock 等) に限定する。カナで定着した語 (エラー / ロールバック / タイムアウト / リトライ / ロック / キャッシュ) はカナへ開く。

| Before | After | 備考 |
|---|---|---|
| `error 判別より前に組み立てる` | `エラー種別の判定より前に組み立てる` | 一般名詞はカナ + 日本語の述語に開く |
| `rollback は insertedOrderIDs を読む` | `ロールバック処理は insertedOrderIDs を参照する` | 概念を指すならカナ + 種別語 (処理 / 経路)。関数を指すなら関数名そのものを記載する |
| `巻き戻し対象が漏れる` (直前で rollback と混用) | 同一 comment 内は「ロールバック対象」で用語統一 | 英語とカナ / 和語の同義語を 1 comment 内で併用しない |

**判断基準**:
- その英単語が同 file 内の識別子を指していないなら、概念を指す一般名詞なので日本語に開く
- 識別子を指すときは識別子の綴りそのまま書く (`CreateAll` / `insertedOrderIDs`)。概念に言い換えるならカナ / 日本語で書き、英語の一般名詞形 (「create 処理」等) にしない
- 同じ概念を英語とカナ / 和語で言い分けない (rollback と `巻き戻し` の混用等)。comment 内で 1 語に統一する

---

### 英語 idiom / business jargon を説明なしで使わない

由来を知らないと意味が伝わらない英語の慣用句・業界用語を identifier や comment に含めない (user 指摘 2026-08-04)。典型は grandfather clause / silver bullet / rubber stamp 等。読み手には辞書的な直訳しか見えず、制度・比喩としての意味が伝わらない。直接的な日本語表現へ置き換えるか、どうしても使うなら意味を日本語で添える。API / commit 等の定着済み技術用語は対象外。

技術用語そのものも、対象 product の公式 doc に無い言い回しなら comment に書かず、役割を日本語で書く (canonical: [PRINCIPLES.md](PRINCIPLES.md) 「用語は初出で開く」 5)。migration の comment に `backing index` と書いて読み手から意味を問われた件が起点で (2026-09-14)、この種の語は [NG-DICTIONARY.md](NG-DICTIONARY.md) 「非公式専門用語 (block)」が hook で block する。

## 体言止め許容ケース

以下の場合は体言止めを許容する。

- godoc の要約行 (慣習的に名詞句で始める、複数行の場合は先頭行のみ対象)
- 短い WHY ラベル (前後の文脈で主語が明確な場合)
- 意味が完結する短い体言止め。回数を合わせる目的では増減せず、羅列で関係が読めない場合だけ文に書き換える

```go
// ProcessBatch はバッチ処理のエントリーポイント ← 1 行 godoc: OK
// rate limit 対策: 100ms スリープ ← 前後でバッチ処理の説明がある: OK
```

## 違反検知: コメント audit 手順

新規 PR やレビュー時に以下の手順でコメントを分類する。

機械検出 (事前 sweep): 抽出したコメントを file に集めて `scripts/jp-textlint.sh <file>` を成功させる (詳細列挙は [PRINCIPLES.md 「機械検出 grep」](PRINCIPLES.md#機械検出-grep-出力前-sweep) canonical)。冗長表現・弱い表現の混入を自動で検出してから、下記の監査カテゴリで精査する。

### 抽出コマンド

```bash
# Go
grep -rn '^[[:space:]]*//' <対象ディレクトリ> | grep -v '_test.go' | head -50

# SQL
grep -rn '^[[:space:]]*--' <対象ディレクトリ> | head -50

# TypeScript / JavaScript
grep -rn '^[[:space:]]*//' <対象ディレクトリ> | head -50
```

### 分類・報告フォーマット

抽出したコメントを以下の監査カテゴリ (本文の「記載する 3 分類」+「削除カテゴリ」に、WHY 移動と AI 生成マーカーを加えた監査用の全量) で分類し、削除 / 書き直し対象を特定する。

| カテゴリ | 判定基準 | アクション |
|---|---|---|
| Why not (記載) | 採らなかった選択肢とその理由 | そのまま (最優先で保護) |
| WHY (移動) | 設計判断の根拠 (なぜこの値 / 順番か) | commit log へ移動してコードからは削除 |
| 重要 memo (記載) | 調べても見つけにくい外部仕様 / incident / 内部運用 | `MEMO:` prefix を付ける。調べれば分かるものは削除 |
| godoc (記載) | 公開シンボルの API doc (行数制限なし) | そのまま。private / 実装詳細は削除 |
| what (削除) | コードの言い換え | 削除 |
| PR 文脈依存 (書き直し) | チケット番号単独 | WHY を 1 文追加 |
| 自明アサーション (削除) | 型から明らか | 削除 |
| defensive 言い訳 (削除) | 「念のため」等 | 削除 + 実装を正す |
| 主観評価 (書き直し) | 根拠なし評価語 | 数値 / 条件に置換 |
| テスト不確実 (書き直し) | 「〜するはず」等 | 検証して断言 |
| 重複 (削除) | 同一概念の複数説明 | 1 箇所に集約 |
| 経過メモ (書き直し) | 「〜から変更」「以前は〜」等の時系列記述 | 経緯を落とし現在形の WHY のみ記載する |
| commented-out code (削除) | コメントアウトされたコード | 削除 (例外時は `TODO:` prefix + 理由) |
| 他宣言参照だけ (削除) | 「理由は X と同じ」等、単体で意味が完結しない | 削除 (理由本文は文脈に近い 1 箇所へ) |
| grep で分かる情報 (削除) | 呼び出し元 / 利用箇所の列挙 | 削除 |
| AI 生成マーカー (削除) | `// AI-generated` 等の生成元表示 | 削除 |

confidence < 80% の判定は discard する (「この行が何カテゴリか不明確」な場合は指摘しない)。
