# 外部発信文章 (PRコメント / Slack / Issue / Notion共通)

共通文章原則は [PRINCIPLES.md](PRINCIPLES.md) 参照。[pr-description.md](pr-description.md) の原則を PRコメント / レビュー依頼 / Slack返信 / Issueコメント / Notion投稿にも適用する。

## 起点

依頼内容と根拠が揃っている場合は、そのまま草稿まで作る。宛先や主張が変わる未決事項がある場合だけ、本文を執筆する前に 1 点確認する。投稿などの外部操作は別途 user の指示を待つ。

## 主管領域チームへの相談 (SRE / DA / Security / Infra など)

主管領域を担当する他 team に判断を相談する Slack / Notion / issue は、確認済みの事実と自分の認識を分け、相手に決めてほしい点を明示する。単純な作業依頼まで相談調に変えない。

### 構成

1. **背景**: 状況説明 + 認識共有 (「〜と考えています」「〜と認識しています」)
   - センシティブ性 / リスク / 制約などの自分側の理解を理由付きで開示する
2. **現状認識**: 前提条件の箇条書き + 「相違あれば指摘いただきたいです」
   - 自分の理解が誤っている可能性を明示し、訂正余地を確保する
3. **ご相談**: 課題提起と、判断に必要な確認点を記載する。件数を合わせるための質問は追加しない
   - 「依頼」「目的」と書かず「ご相談」「教えていただけると助かります」

### トーン

| 避ける | 使う |
|---|---|
| 目的: 〜すること | 〜と考えています / 認識しています |
| 依頼: | ご相談: |
| 〜してください | 〜していただけると助かります |
| 〜の手順を提供 | 〜の手順を教えてください |
| (前提を断定) | (前提) と認識しています、相違あれば指摘いただきたいです |
| 必須 / 必要 / すべき | 必要があると認識しています / 〜と考えています |

## 構造 (ストーリー型)

短文向けの基本構造 (PREP や媒体別構造の詳細は [PRINCIPLES.md](PRINCIPLES.md#媒体別構造) 参照):

- 結論や依頼を先に置き、必要な根拠を続ける
- 時系列が重要なら「現状 → 取った対応 → 確認したい点」を使う
- 並列の事実は箇条書き、因果関係や判断理由は段落で書く。構造を合わせるために内容を分断しない
- 本文が箇条書きで、各項目に理由や補足が付くときは段落に戻さず、上位 bullet に結論 1 文を配置して理由と補足を下位 bullet に置く (1 bullet に 3 文以上を詰めない。判定は [PRINCIPLES.md](PRINCIPLES.md#箇条書き階層化) の pattern 4)

## 用語の自然文化

- **コード識別子をコードフェンスで並べない**、自然文に溶かす
- 専門用語は最小限、レビュアーが詳細を知らない前提で書く
- 技術語は平易語に置換 (詳細置換表は `references/writing-patterns.md` 参照可、簡易は下表)

| NG (用語羅列) | OK (自然文化) |
|---|---|
| `clone_products.sql` の `ORDER BY id` を `migrate_slots` の `rand.Shuffle` に合わせる | 並び順を本番に合わせる方式に統一した |
| `BASE_URL` / `BRANCH_NAME` 未指定でinit context throw | 接続先と環境タグを未指定で起動した場合に停止する |
| VU / SKIP LOCKED / DBロック | 同時実行ユーザ / 先頭から空き行を順に取る仕組み / DBのロック競合 |

## GitHub auto-link 衝突を避ける

PRコメント / Issue / Slackで `#1234` 形式の番号を本文中に記載すると、GitHubが同repoの issue / PRへの auto-link を付ける。意図しない link 接続を防ぐため:

| 場面 | 書き方 |
|---|---|
| 同repoの issue / PRを参照 | `#1234` (auto-link 期待) |
| 他 repoの issue / PR | `owner/repo#1234` (cross-repo auto-link、repo 名明示) |
| DD 内部の section 参照 (例: Section 9-2 #5) | `` `#5` `` (バッククォートescape、auto-link 抑止) |
| 番号だけの参照 (例: 「項 #3」) | `` `#3` `` (escape) |

**判断**: 番号 literal を記載する前に「当該番号は GitHub issue / PR の番号か、本文内の項番号か」を判定し、項番号なら必ず escape する。

## link 過多を避ける

link は本文の主張に直接必要なものだけ掲載する。網羅的に付けると読み手に不要な情報が本文を侵食し、結論が見つけにくくなる。

- 「補足参考」レベルの link は末尾 `<details>` 折りたたみに移動するか削除する
- PR chain は先頭 PR 1 つだけ付け、後続 PR は先頭 PR から開いてもらう
- 同一 file / PR への link は初出のみ。2 回目以降は文字参照にする
- self-check: link を外しても主張が成立するなら、その link が読み手の次の行動に必要か見直す

## Issue 起票時の追加規約

bug report / feature request の Issue は、コメントより構造化が必要。下記 3 点を必ず満たす。

| 項目 | ルール |
|---|---|
| **再現手順** | 再現に必要な前提と操作だけを記載する。別の故障や前提が混在する場合は Issue 分割を検討 |
| **期待値 / 実測値分離** | `## 期待` `## 実測` を必ず別 section に分ける。混在すると判断と事実が区別できず、再現確認が止まる |
| **環境情報** | OS / app version / commit hash / 関連 config を冒頭 1 ブロックに固める。bug 系は特に必須 |

feature request は `Why (現状の不便) / What (期待動作) / How (案がある場合のみ)` の 3 セクション。How が無い request も受け入れる (議論余地を確保する方が良い案が出る)。

## 文長・記号

- 長い文は読み違えが起きる所で分け、段落は 1 主張に限定する。文字数や文数を揃えない
- 過剰な記号 (🙏 / — の連発 / 顔文字) は排除。禁止対象は装飾的な記号で、表セル内の判定記号 (⚠️ 異常 / ✅ 余裕、下の 「Issue コメントで調査結果を共有する書き方」) は評価表示として使える
- 感嘆符 (`!` / `！`) の連発を避ける (blog / 社外公開 scope。技術文書向けの `writing-sentence-rules.md:139` を blog にも適用する意図)
- 太字見出し + 箇条書きでscanしやすく

## 最終チェック (投稿前、5軸採点)

観点本文の正本は [PRINCIPLES.md](PRINCIPLES.md) 「推敲5観点」。短文投稿では次の日本語ラベルで対応づける。

| 短文ラベル | 推敲5観点 | 短文での見方 |
|---|---|---|
| 可読性 | [A] readability | 1文の長さ・段落の塊感 |
| 視認性 | [B] visibility | 階層・記号・太字の使い方 |
| 伝達性 | [C] signal | 知識前提の最小化、専門用語の平易化 |
| 根拠性 | [D] evidence | 主張が確認済みの事実・数値・URL・commitで支えられているか。無い根拠を作っていないか |
| 整合性 | [E] coherence | section重複なし、起点の合意通り |

5 軸は見落としを探す観点として使う。合計点や各軸の点数を合格条件にせず、投稿内容に実害がある指摘だけ直す。

共通セルフチェックは [PRINCIPLES.md](PRINCIPLES.md#出力前セルフチェック) 参照。Web 出力時は `## Web 可読性` の追加項目も確認する。

## 投稿前ワークフロー

1. 宛先・目的・根拠を確認する
2. 本文を作り、5 軸と共通セルフチェックで見直す
3. 草稿を提示する。確認過程や採点は本文に含めない
4. user の明示指示後に投稿する

## Issue コメントで調査結果を共有する書き方

技術調査結果 (Datadog / APM / 負荷試験結果など) を Issue コメントで PM / 非エンジニアも読む状態で共有するときは、**「実測値 → つまり (解釈) → アクション」の 3 段構成**にする。技術データだけ並べると読み手が判断できず意思決定が拡散する。

### テンプレ

```markdown
## XXX 分析 (YYYY-MM-DD 追加調査)

[調査のきっかけと範囲を 1-2 行]

### 実測値

| 項目 | 実測値 | 評価 |
|---|---|---|
| ... | ... | ⚠️ 異常 / ✅ 余裕 |

### つまり

[技術用語抜きで、何が起きていたかを平易な日本語で 2-3 段落]
[可能なら前向きにフレーミング (「最悪ケースでも壊れない強い保証」等)]

### アクション

| 確認項目 | 内容 | 優先度 |
|---|---|---|
| ... | ... | P1 緊急 / リリース前確認 |

[最後に 1 文で締める]
```

### 有効なパターン

- **「つまり」段落で意訳**: 「試験はアプリサーバー 1 台だけで動いていた状態」のような平易表現
- **異常を前向きにフレーミング**: auto-scale 不発 (異常) → 「最悪ケースでも壊れない強い保証」
- **平易な比喩**: 「片肺運転」「1 台だけで動いていた」
- **表で raw data、地の文で解釈**: 数値は表に閉じ込め、本文は判断・意思決定に集中
- **評価列の絵文字**: ⚠️ 異常 / ✅ 余裕 で視覚的に判定を示す
- **前向きな結語**: 「これらが想定どおりであれば〜」で締める。恐怖を煽らず行動を促す

### やってはいけない

- 技術データだけ表で並べて解釈なしで終わる (読み手が判断できない)
- 異常発見を負の表現だけで書く (「壊れる可能性」だけだと意思決定が止まる)
- 1 セクションに raw data + 解釈 + アクションを全部入れる (3 段に分ける)
