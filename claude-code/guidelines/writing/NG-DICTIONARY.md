# NG 辞書

hook (`lib/jp-quality/term-extraction.sh:_extract_term_list`、`hooks/pre-tool-use.sh` が `lib/jp-quality-check.sh` 経由で source) が動的抽出する NG 語 list。key 名・記法を 1 文字も変えない。

執筆論・使用指針は [PRINCIPLES.md](PRINCIPLES.md) 参照。

**AI定型語**: 効果的に / 効率的に / シームレスに / 直感的に / 革新的な / 素晴らしい / 強力な / より良い / 〜を実現します / 〜を提供します / 〜を可能にします / 〜することができます / ご紹介します / ご覧ください / 〜いただけます / 重要なポイント / 注目すべき点 / 本機能は / 本ドキュメントは / 本記事では / 本稿では〜について述べる / 包括的な / 堅牢な / 柔軟な / スケーラブルな / 最適化 / 影響なし / 収まる / 外挿 / 余裕大 / 無視可 / 無視可能 / 懸念解消 / 全観点 / 判定確定 / 漸近

**断定語 (warn-only)**: 完了 / 解消 / 見込み / クリア / 問題なし / 完了,問題なし

> 連続漢字≥5 の頻出 NG 例 (structural warn 対象、warn-only): 動作確認手順 / 回答案検討 / 回答案確定 / 対応方針決定 / 参照箇所影響範囲確認 / 上流下流関係 / 再投稿完了 / 同梱未対応。「動作の 確認手順」「回答案を 検討」のように助詞挿入か訓読み開きで分解する。

**英語jargon (warn-only)**: digest / inject / sweep / canonical / trigger / fan out / fan-out / stale / orchestrate / delegate / salience / priming / fallback / dedup / throttle / insight / takeaway / deep dive / edge case / align / gate / adopt / evidence / drift / triage / maintenance / cost / cap / prose / mask / bullet / green / schedule / headless / guard / foreground / fire / feat / durable / resolve

> 英語jargon は warn-only。日本語で言える一般語は日本語化する (digest→要約 / inject→差し込む / sweep→点検 / canonical→正 / trigger→きっかけ / stale→古い / fallback→代替 / edge case→境界事例 / align→そろえる / gate→判定 / adopt→採用 / evidence→根拠 / drift→乖離 / triage→仕分け / maintenance→保守 / cost→コスト / cap→上限 / prose→地の文 / mask→伏せる / bullet→箇条書き / green→通る / schedule→定期実行 / headless→非対話 / guard→保護 / foreground→フォアグラウンド実行 / fire→発火する / feat→機能 / durable→永続的な / resolve→解決する)。gate 以降の 12 語は unknown-en 頻出集計 (2026-07-20) を根拠に追加した。schedule 以降の 7 語は launchd 系 commit (e474776 以降) 由来の unknown-en 頻出集計 (2026-07-21) を根拠に追加した。macOS 固有識別子 (launchd / kickstart / plist) は先回り whitelist 化せず backtick 回避で対応する。`feat` は commit prefix (`feat:`) では正当なため、地の文で「feat」と書いた場合のみ対象とする (grep は語境界判定)。識別子・command 名として正当に使う場合は backtick で囲むと検査対象外になる。追加根拠は user 指摘「専門用語使いすぎ」(2026-07-10) の incident。chat 経路はこの denylist に加えて許可一覧方式を併用する。`guidelines/writing/allowed-en-terms.txt` (ジュニア IT エンジニアが分かる定着語のみ、user 決定 2026-07-19) に載らない小文字英単語も warn になる (`lib/jp-quality/block-checks.sh:_check_unknown_en_terms`)。

**主体不明断定 (skill-only)**: 多くの〜 / 一般に〜 / 一般的に〜 / よく〜される / 〜と言われる / 〜だろう / 〜と考えられている

> `(skill-only)` mode は hook 抽出対象外。`/jp-fix` skill self-check 経由でのみ参照する。技術 README 等で正当な総称表現として使う場面があり、hook 自動 block / warn は誤爆コストが高いため。語源は PRINCIPLES.md `## AI臭の根本: 書き手不在` `(1) 主体を明示する`。

**主体不明断定 (warn-only)**: と言われる / と考えられている / とされている

> hook (chat 経路) が warn する grep-safe subset。上の skill-only key は「〜」placeholder 入りで literal grep に載らないため別 key として分離した。「一般的に」「だろう」は正当用法が多く誤爆コストが高いので含めない。

**jp-fix 固有 NG (skill-only)**:

| NG | OK |
|----|-----|
| 体言止め圧縮による擬人化 (`flag 未渡しが実行を走らせない`) | 主語を明示し使役展開する (`flag を渡さない場合、実行されない`) |
| 連用形否定 (`未渡し` / `未指定時`) | 「指定されなかった場合」と展開する |
| 口語動詞 (`倒す` / `握る` / `走らせる`) | 書き言葉に置換する (`無効化する` / `保持する` / `実行する`) |
| 英単語 + `する` の動詞化 (地の文で `commit する`) | 日本語動詞に置換。識別子・コマンド名はバッククォート囲み、動詞化しない |
| 英単語 + `化` の圧縮 (`true 化しない` / `slot 化`) | 主語のある文に開く (`true を返さない`)。可視化 / 標準化 / 非同期化など定着した業務用語はそのまま使う |
| 専門用語 (異職種向け): `fail-closed` / `TX` / `dead code` | 安全側で止める / トランザクション / 使われていない code。識別子・コマンド・DBカラムは維持 |
| 社内造語: `派生値` | `計算値`。外向き文書は平易化 |

> worktree や branch を消す動作を「畳む」、使われていない code を「死蔵」、link されていない file を「孤児」と書かない。それぞれ「削除する」「使われていない」「どこからも link されていない」と動作や状態で書く。「畳」は 1 文字で登録し、折り畳み / 畳み込む / 名詞句に畳む等の全活用形を検出する (UI の details 要素は「`<details>` で閉じる」、統合は「組み込む」「まとめる」と書く)。口語の圧縮動詞 5 つ (`流す` `倒す` `詰める` `引く` `寄せる`、canonical: [PRINCIPLES.md](PRINCIPLES.md) 「口語の圧縮動詞」) も終止形と て / た 形で登録し、渡す / 出力する / 安全側にする / 該当するものを特定する / 入れる / 取得する / release に分かれる」「両方の PR に含まれる」「境界を越えない」のように何がどう分かれているかで書く (user 指摘 2026-09-07)。「漏れ」は確認漏れ / テスト漏れ / 漏れる の全形を検出し、「未確認の項目」「不足しているテスト」「対象に入っていない」のように何が足りないかで書く。「黙る」は処理や hook を擬人化した言い方 (黙って skip する、hook が黙る) で、「通知せずに省略する」「検出しない」と動作で書く。「黙」1 文字で登録すると「暗黙」に当たるため活用形で登録する (user 指摘 2026-09-07)。「誤」1 文字を英語に付けた圧縮 (誤 sync / 誤 merge / 誤 block) も禁止で、「誤って sync した」「意図しない merge」「本来は通すべき block」のように文で書く。「誤って」「誤り」「誤検知」「誤判定」は日本語の語として成立しているので対象外。検査は固定文字列の部分一致で語末の空白を保持できないため、実際に出た連結形を列挙して登録する (user 指摘 2026-09-07)。他動詞の終止形と て / た 形だけでは自動詞形と可能形が素通りするので、流れる / 倒れる / 詰まる / 引ける も同じ 3 形で登録する (stdout が流れる → 出力される、安全側に倒れる → 安全側にする、pipeline が詰まる → 止まる、grep で引ける → 検索できる、と書く)。「漏らす」は「漏れ」に部分一致しないので別に登録する。「誤 + 英語」の連結形は repo 本文だけでなく commit message と memory からも洗い出し、動作の圧縮 (誤 approve / 誤 reject / 誤 warn / 誤 excerpt / 誤 re-install / 誤 archive) と 「誤った X」の圧縮 (誤 baseline / 誤 REGRESSION / 誤 FAIL / 誤 file / 誤 path / 誤 project) の両方を登録する (user 指摘 2026-09-07)。値や状態を物のように動かす 9 > 「出す」「外す」「持つ」「見る」「入れる」「切る」は意味の範囲が広く、実際の操作を読み手が文脈から復元しなければならない。実際の処理を表す動詞に置き換える: 値を出す → 返す / 生成する / 取得する / 表示する、処理を外す → 削除する / 無効化する / 分離する / 対象外にする、データを持つ → 保持する / 所有する / 格納する、チェックを入れる → 検証する / 条件を追加する、branch を切る → 作成する、PR を見る → レビューする / 確認する。日本語は語境界がなく部分一致で検査するため、「検出した」「区切って」「受け入れて」への誤爆を避けて助詞付き (を / に) の形で登録する。助詞なしの「PR 出す」は拾わないが、外向き text ではほぼ助詞を伴う (user 指摘 2026-09-06)。

> 文末の断定「〜だ」も block する (user 指示 2026-09-12)。PRINCIPLES.md 「plain JP の文体」 が 2026-08-03 から「〜だ」で閉じないと定めていたが、検査に接続しておらず hook が検出できなかった。言い換えは動詞終止 (「〜する」「〜した」「〜ある」) か「〜になる」「〜として扱う」で、名詞述語なら「〜が対象になる」「〜を指す」のように動詞へ開く。

>

## 偶然一致 (false positive) 回避

hook の match logic は `grep -ioFf` (substring・case-insensitive)。技術用語 / skill 名 / library 名が NG 語を内包すると hit する (例: skill 名「robust-XX」が `robust` に hit、prose 内の `leverage` を含む製品名 / API 用語等)。

### 回避優先順位

hit した語が**地の文か、識別子か、上流 doc からの逐語引用か**で先に分岐する。識別子でも逐語引用でもないのに backtick で囲むと、hook は検査対象から外すが読み手には NG 語がそのまま残存する。

1. **地の文の hit (default)**: 検出語を含む**文を単位に書き直す**。語だけを別の語へ差し替えると、同じ問題が別の語形で残り、前後の係り受けが壊れる。置換候補は書き直しの方向を示すもので、そのまま貼り替える対象ではない。
   - 例: `本機能は効率的に処理を行うことができます` → ✗ 語だけ差し替えた `本機能は効率よく処理をします` / ○ 文ごと書き直した `1 件あたり 200ms で処理する`
2. **識別子の hit**: 技術用語 / command 名 / 固有名詞は backtick で囲む。`_strip_code_blocks` が ` `code` ` / ` ```block``` ` を除去するため hook をすり抜ける。commit message / PR / Slack / Notion / DD / RCA すべて適用。囲ってよいのは、その語が識別子として画面や command に現れる場合だけにする。
   - 例: `leverage を使う` → ✗ block / `` `leverage` ライブラリを使う `` → ○ pass
3. **上流 doc からの逐語引用**: Design Doc の受け入れ条件のように、上流 doc の文言を一字一句そのまま転記する箇所は backtick で囲む。引用の語の責任は上流の書き手にあるので、辞書に合わせて言い換えると引用でなくなり、読み手が上流 doc と照合できなくなる。囲ってよいのは上流に同じ文が実在して完全に一致する場合だけにし、要約・省略した箇所は書き手の文なので 1 に従う。上流 doc の側に NG 語が入っているなら、上流を書き直して引用を取り直す
   - 例: SPEC の完了条件が Design Doc の AC を指す → ✗ 言い換えた `` AC-1「取得が存在しない」`` / ○ 原文のまま `` AC-1 `取得が残っていない` ``
4. **whitelist 追加 (incident base 限定)**: 1, 2 で吸収できず**かつ同じ語で 3 回以上 false positive 実害**が発生した時のみ、本 file に whitelist section を新設して exact match 除外する。先回り whitelist 化禁止 (hook 機能後退の温床)。

### canonical 運用

- skill 名 / agent 名 / library 名 / API method 名 を**外向き prose に bare 出現させない**。code fence 内に閉じ込めるか日本語説明に置換する
- block 発生時の retry は本 section の優先順位に従う (whitelist 提案を先に出さない)
- `~/.claude/logs/jp-quality-block.log` に hit 履歴が保存される。同語 3 回到達後に whitelist 化を再評価する。数えるのは `block` 行だけとする。`record-only` 行は遮断が無効なときの検出記録で、実害が出た回数ではない
